# study4（仮）計画メモ: 用途限定の自作LLMドライバでAiderのパーサー誤爆を解決する

> このファイルはZenn記事ではなく作業用メモです（`notes/`配下はZenn CLIの対象外）。
> 作成日: 2026-07-19

## 背景・動機

study3 / study3-a を通じて、Aider + ローカルモデル（Ollama）の失敗を4パターンに分類してきたが、
**最も頻発したのは「whole形式パーサーの誤爆」というハーネス起因の失敗**だった。

観測された実績:
- Ornith-1.0-9B: カルマンStage1で1回（「戻り値: (x, P)」というファイル名のゴミファイル生成）
- gemma4:e2b-mlx: カルマン・SVDの**両タスクとも初回に発生**（0バイトファイル+ゴミファイル、`### svd.py`見出し形式を認識できず「変更不要」と空虚な成功報告）

重要なのは、**これらのケースでチャット履歴を調べると正しい（または惜しい）コードが生成されていた**こと。
モデルの能力ではなく「モデル出力 → ファイル書き込み」のインターフェース層で成果物が失われている。

この層を構造的に排除する、用途限定の自作ドライバを作り、同一タスクでAiderと成功率を比較するのがstudy4。

## 設計原則（観測された失敗からの逆算）

| 観測された失敗 | 対応する設計 |
|---|---|
| whole形式のパース誤爆（ファイル名とフェンスの曖昧さ） | **1リクエスト=1ファイル** + **system promptによる出力制約**（フェンス・ファイル名見出しなし、生内容のみ）。markdownフェンスの解析をパースの主手段にしない（M1でJSON schemaはMLXバックエンド非対応と判明、代替設計に変更） |
| ①テスト改竄（qwen2.5-coder:7b） | テストファイルのハッシュをループ外で保持し、変更されたら即FAIL |
| ②空虚な成功（gemma4:e2b） | 生成テストをAST解析し、テストメソッド0件・本体pass・assert 0件を検出したら再生成 |
| ③許容誤差の隠蔽（e4b-mlx: 1e-8→10.0） | イテレーション間でassert行の数値リテラル差分を検出し、緩和方向の変更は警告+ログ |
| ④ゴミファイル生成 | 書き込み先は指定ファイルのみ（ワークスペースのスナップショット比較で検証） |
| 同一セッション内で失敗パターンに固着（study3: 6回目のリセットで解決） | リトライ戦略に**セッションリセットを組み込む**（同一会話2回→履歴破棄して新規1回→FAIL） |
| **[2026-07-19 M2で新規発見]** テストファイルが実装ファイルをimportせず、自前で（同じ欠陥のまま）関数を再実装していた。実装をいくら修正してもテストは常に同じ理由で失敗し続けた | **G5（新設）**: テストファイルのASTを解析し、`from {impl_module} import ...`または`import {impl_module}`が存在することを確認。なければG2と同様に再生成 |

## ツール仕様

### 名前・場所
- 仮称: **monocoder**（1ファイル限定という設計思想から。決定は実装時でよい）
- 場所: `~/dev/monocoder/`（zenn-contentとは独立。記事はzenn-content側に書く）

### 技術選定
- Python 3.9+（**標準ライブラリのみ**: urllib.request, json, ast, hashlib, argparse, subprocess）
  - 依存ゼロにする理由: このマシンのpython/pipはIntel版という環境問題（[[env-arm64-rosetta-mismatch]]）を踏まないため、またツール自体の再現性のため
- Ollama `/api/chat` を直接呼ぶ

  **[2026-07-19 M1で判明・設計変更]** 当初案の「`format`パラメータにJSON schemaを渡して構造化出力を強制」は、**MLXバックエンドでは機能しないことが判明**した。
  ```
  gemma4:e2b（GGUF, 通常版）   → format schema 動作: OK（正しくJSONを返す）
  qwen2.5-coder:7b（GGUF）    → format schema 動作: OK
  gemma4:e2b-mlx（MLX）       → format schema 無視、プレーンテキストで返る
  gemma4:e4b-mlx（MLX）       → format schema 無視、プレーンテキストで返る
  gemma4:e2b-mlx + format="json"（簡易モード） → さらに壊れた出力（fence/prefixが混入）
  ```
  Ollamaの構造化出力（grammar制約デコード）はllama.cpp（GGUF）バックエンドの機能で、MLXバックエンドには未実装と見られる。study4の主役はe2b-mlx/e4b-mlxのため、JSON schemaには依存できない。

  **代替設計**: system promptで「生ファイル内容のみ、フェンス・説明・ファイル名見出しなし」を強く指示し、応答をほぼそのままファイルに書く。念のため防御的に先頭/末尾の\`\`\`フェンス行だけ除去するフォールバックを入れる（fence自体をパースの主手段にはしない）。スモークテストではe2b-mlxがこの指示だけで一発でフェンスなしの綺麗なコードを返した。「1リクエスト=1ファイル」という制約自体がAiderの曖昧さ（複数ファイル・ファイル名とフェンスの境界解釈）の大半を解消しており、JSON schemaは元々「なくても十分」だった可能性がある
- 応答は原則そのまま書き込み、フェンス行が残っていた場合のみ正規表現で除去する防御的ポストプロセスを通す
- 固定パラメータ: `temperature: 0.1`, `num_ctx: 32768`（書籍6章の知見を踏襲）

### CLI設計

```sh
# 単発生成（1ファイル）
monocoder gen --model gemma4:e2b-mlx --out svd.py --prompt-file task.txt

# テスト駆動ループ（実装+テストを別リクエストで生成→unittest実行→失敗時は修正ループ）
monocoder tdd --model gemma4:e2b-mlx \
    --impl svd.py --test test_svd.py \
    --impl-prompt impl.txt --test-prompt test.txt \
    --test-cmd "python3 -m unittest test_svd -v" \
    --max-iter 3 --max-session-resets 1

# 3段階パイプライン（study3の計画→実装+テスト→ドキュメント化を1コマンドで）
monocoder pipeline --model gemma4:e2b-mlx --config kalman_pipeline.json
```

### tddループの内部フロー

```
1. 実装ファイル生成（1リクエスト、system promptで生内容のみを制約）
2. テストファイル生成（別リクエスト、同様の制約）
   → ガードG2: AST解析（テストメソッド>=1、pass-only本体なし、assert>=1）。違反なら再生成
   → ガードG1: テストファイルのSHA256を記録
3. test-cmd実行
4a. PASS → ガードG1再検証（テスト無改変）→ 成功終了
4b. FAIL → 失敗出力+現ファイル内容を渡し「実装ファイルだけを修正した全文」を要求（テストは渡すが編集対象にしない）
   → ガードG3: 修正がテスト側に及んでいたら拒否してログ
   → 3へ戻る（max-iterまで）
5. max-iter超過 → 会話履歴を破棄し、手順1から新規セッションで再試行（max-session-resetsまで）
6. それでも失敗 → FAILとして全ログを保存して終了（silent failureにしない）
```

### ログ・監査
- 全リクエスト/レスポンス、ガード発火、リトライ理由をJSONLで`runs/<timestamp>/`に保存
- 記事執筆時にこのログがそのまま一次資料になる

## 検証計画（study4本編）

### タスク・比較条件
- study3と同一のカルマンフィルタ・SVD（ランク1近似）タスク、同一の指示文（プロンプトはAider版から流用し、編集形式に関する文言のみ調整）
- 3段階プロセスも同一（計画→実装+テスト→ドキュメント化）

### 対象モデル（3つ）
| モデル | 狙い |
|---|---|
| gemma4:e2b-mlx | **主役**。Aiderでパーサー誤爆が2/2タスクで発生した最不安定モデル。自作ドライバで安定するかが記事の核心 |
| gemma4:e4b-mlx | Aiderでは安定していたモデル。自作ドライバで品質が落ちないこと（非劣化）の確認 |
| ornith:9b | 要再pull（5.6GB、空き46GBで問題なし）。書籍の推奨モデルでの動作確認を兼ねる |

### 評価軸
1. **パーサー系失敗の発生率**（Aider実績: e2b-mlxで2/2 → 目標0）
2. タスク完遂率（テストPASSまで到達したか）とガード発火回数
3. 生成時間（Aider経由との差）
4. 生成物の品質（実装・テストを目視+独立検算。SVDのアルゴリズム設計ミスのようなモデル起因の失敗は「ドライバでは防げない」ことの確認材料として記録）

### 予想される結果（仮説、実測で検証）
- パーサー系失敗はゼロになる（構造的に発生し得ない）
- ただしe2b-mlxのSVDアルゴリズム設計ミス（モデル起因）は自作ドライバでも再現するはず → 「ハーネスで防げる失敗と防げない失敗」の境界が記事の結論になる
- プロンプトのみでの制約なので、複雑なタスクで説明文が紛れ込む可能性はゼロではない（防御的フェンス除去で吸収する想定、M2で実データ検証）

## 現状の課題（2026-07-20時点、事実と推測を区別）

### 確認済みの事実
- JSON schema強制(`format`)はMLXバックエンドで無視される（GGUF系では動作）
- パーサー崩壊は全12回の実行で0件（設計通り）
- `think`未指定によりornith:9bが特定プロンプトで思考に生成予算を全消費し、回答本体を生成しないことがある（条件A/B/Cの切り分けテストで確認）
- `think:false`修正後もmonocoderの成功率はAider実績（study3/3a）より明確に低い（6回中1回）
- 修正後の各FAILの表面的な症状は個別に確認済み（e2b-mlx kalman: 共分散行列の次元崩壊、e2b-mlx svd: 精度不足、e4b-mlx svd: 非正方行列での形状不一致、ornith:9b kalman: impl/testの型不整合、ornith:9b svd: 数値精度不良）が、根本原因はいずれも未追跡

### 未検証・推測
- think:false適用前後で3/6タスクの成否が入れ替わった件が、think:falseの副作用か単なるrun-to-runのばらつきかは未切り分け（各条件1回ずつしか実行していない）
- think:falseがMLX版gemma4（e2b-mlx/e4b-mlxもthinking capability持ち）の回答品質を下げている可能性は未検証
- Aiderがornith:9bの思考暴走を踏まなかった理由（内部でthink制御しているか、プロンプト差でたまたま踏まなかったか）は未調査
- monocoderの成功率の低さが、実装/テスト独立生成・システムプロンプトの拘束力・max-iter設定など、どの設計要素に起因するかは未特定

## 要因分析と改善実装（2026-07-20、第2ラウンド）

### ログから確定した要因（事実）
| 要因 | 根拠 | 対応 |
|---|---|---|
| A. fix-loopがテストファイルの中身を見せず、unittestの出力だけでインターフェースを推測させていた | `fix_instruction`のコード確認。修正後失敗の4/5がインターフェース不一致系 | **修正済み**: fix promptにテスト全文を含める |
| B. session resetで実装だけ再生成し、旧テストをpinしたまま→シグネチャ乖離が構造的に発生 | e2b-mlx svdで実測（新実装が3引数、pinテストは1引数呼び出し） | **修正済み**: resetでテストも対で再生成・再pin |
| C. フェンス除去が先頭/末尾のみで、ファイル中間の``` 混入を見逃す | e2b-mlx svdの1回目FAILが154行目のSyntaxError | **修正済み**: .pyはast.parse検証→失敗時のみ全フェンス行除去を試す（salvage_python_syntax） |
| D. テストプロンプトに実装全文を見せると、モデルが「同ファイル内で利用可能」と誤解しimportをコメントアウト | e2b-mlx kalman再実行で3世代連続で観測 | **修正済み**: system promptに「参照用であってこのファイルでは使えない。importを絶対にコメントアウトしない」を明記 |
| E. ガード却下時のリトライが同一プロンプト再送→temperature 0.1では同じ誤りを繰り返す | 同上（3回連続同一違反） | **修正済み**: 却下理由をリトライプロンプトに追記するフィードバックループ |
| F. G2(AST)はimport漏れを検出できない（`import unittest`なしでもassert存在チェックは通る） | e4b-mlx kalman再実行でNameErrorが6イテレーション浪費 | **修正済み**: G6（pin前にサブプロセスでimport実行するスモークチェック）を追加 |

### 残る本質的課題（ツールでは防げない・要検証）
1. **テスト前提の誤り**（例: e2b-mlxが「predictのみで共分散が減る」というカルマンフィルタの数学に反するテストを書く）。ガードで機械的に検出できない。study3でgemma4:e2bのテスト設計力の弱さとして既観測——Aider時代も人間介入で解決していた
2. **Aiderとの成功率比較のフェアネス**: study3のAider「成功」には (a)人間の介入（gemma4:e2bのテストは最終的に人間が書いた）、(b)偽陽性PASS（e4b-mlx svdは許容誤差10.0への改竄で見かけ上PASS）が含まれる。monocoderのFAILは正直な失敗報告であり、見かけの成功率差は実力差をそのまま表さない
3. run-to-runばらつきの定量化（n=1問題）。同一条件複数回の実行が必要

## リスク・未知数
