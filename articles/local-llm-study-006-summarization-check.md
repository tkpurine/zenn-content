> **結論**: 要約の「3〜5個の箇条書き」という緩い指示には、試した6モデルが3回とも従った。しかし「ちょうど3個・各80字以内」「スライド5枚・番号付きタイトルのみ」のような厳しい形式の指示では、モデルごとに結果が割れ、モデルの大きさでは説明できなかった。最初の測定(1回)で見えた「指示を無視した」という結果は、今回の条件では再現しなかった。
>
> **読者が得るもの**: 要約・資料作成にローカルLLMを使うときに、形式の指示をどの強さで書けばよいか、モデルを替えると何が起きるかの実測。形式を機械的に検査するスクリプトの考え方。

## この記事について

これまでの検証(study1〜5)はコーディング関連のタスクでした。この記事では、「資料作成・要約」という別の用途を扱います。最初の版は1タスク・1回の測定だけで、「gemma4:e4bとqwen3.5:9bは指示を無視した」と結論していました。その結論が1回の偶然ではないかを確かめるため、プロンプトを3種類に増やし、各3回、モデルを6つに広げて測り直しました。判定は、箇条書きの数や長さなどの形式だけを機械的に数えるもので、内容の正確さは見ていません。

## 最初の測定(元の版)

自作の技術記事(study2、約8,400文字)を渡して、「3〜5個の箇条書きで日本語要約してください」と指示し、Ollama APIに直接投げました。

| モデル | 所要時間 | 結果 |
|---|---:|---|
| gemma4:e4b | 93秒 | 長大な報告書を生成し、箇条書きの指示を無視 |
| qwen3.5:9b | 178秒 | 回答が空(`done_reason: "length"`)。思考が生成の上限を使い切った |
| qwen3.5:9b(`think: false`) | 112秒 | 回答は出たが、同様に長大な報告書で指示を無視 |

qwen3.5:9bで、`think: false` を指定しないと回答が空になる、という点は、Ornith系で見たのと同じ症状でした。今回の測り直しでは、最初から `think: false` を指定しています。

## 測り直しの条件

- 入力: 同じ記事(8,339文字を固定したコピー)。`num_ctx` は16384、生成の上限は2048トークン、温度は0.1
- 試したモデル: Qwen3.5の2B・4B・9B(Unsloth、Q4_K_M)、LFM2.5-24B-A2B(UD-Q2_K_XL)、Qwen3.8-27B(UD-Q2_K_XL)、gemma4:e4b(Ollama公式)
- 各プロンプト3回ずつ(最初の1回はモデルの読み込み時間を含み、2回目以降が実質の速度)

| 名前 | プロンプト | 合格の条件 |
|---|---|---|
| base | 3〜5個の箇条書きで要約 | 箇条書きが3〜5個 |
| strict | ちょうど3個、各80字以内、前置き・見出し・表・絵文字・まとめなし | 3個で、各80字以内、箇条書き以外の行がない |
| slides | スライド5枚の構成案。「1. タイトル」の形式で、説明文や見出しなし | 番号付きの行がちょうど5つで、他の行がない |

## 結果

合格した回数(3回中)です。

| モデル | base | strict | slides |
|---|---:|---:|---:|
| Qwen3.5-2B | 3 | 0 | 0 |
| Qwen3.5-4B | 3 | 3 | 3 |
| Qwen3.5-9B | 3 | 0 | 3 |
| LFM2.5-24B-A2B | 3 | 2 | 3 |
| Qwen3.8-27B | 3 | 3 | 0 |
| gemma4:e4b | 3 | 3 | 0 |

baseは全モデルが3回とも合格でした。最初の版で「無視した」とされたgemma4:e4bとqwen3.5:9bも、今回は3〜5個の箇条書きで答えています。差が出たのは、厳しい指示の2つでした。

### strict: 「各80字以内」で割れた

箇条書きの数は、LFMの空の1回を除き、すべて3個でした。落とした原因は文字数で、Qwen3.5-2Bは98〜113字、9Bは83〜106字と、3回とも上限を超えました。一方4Bは70〜78字、gemma4:e4bは63〜67字、Qwen3.8-27Bは59〜62字で収まっています。モデルが大きいほど守る、という並びにはなっていません。9Bが守れず、4Bが守っています。

LFM2.5は1回、回答が空でした(`finish_reason` が `length`)。LFMは思考を止められないモデルで、生成の上限を思考で使い切ったと考えられます。この点はstudy11で見た性質と一致します。

### slides: 3つの落ち方

- **Qwen3.5-2B**: `# 1. タイトル` の下に説明文を書く形式で、見出しを使い、10行の出力になりました。「説明文や見出しなし」を守れていません。
- **gemma4:e4b**: スライドのタイトルを5行、きちんと書きましたが、番号が付いていませんでした。内容は指示どおりの5枚で、番号という書式だけ落としています。判定は機械的なので不合格ですが、人が使うなら実質的には許容できる出力です。
- **Qwen3.8-27B**: 「ちょうど5枚」を無視して、9枚の構成を3回とも出しました。形式は番号付きで正しいものの、枚数が違います。

### 速度

2回目以降の所要時間は、2B・4Bが数秒、9BとLFMが7〜23秒(strictとbase)、Qwen3.8-27Bが21〜67秒でした。gemma4:e4bはbaseで約5秒、strictとslidesは1〜3秒でした。最初の1回は、モデルの読み込みを含むため、45〜240秒かかっています。

## 考察

最初の版の結論と今回の結果は、はっきり食い違います。同じ指示文と同じ入力でも、今回は「3〜5個の箇条書き」に全モデルが従いました。違いとして考えられるのは、温度(今回は0.1)や、モデルの取得元(qwen3.5:9bは今回Unsloth版)、`think: false` の指定などですが、どれが原因かは切り分けていません。確かなのは、最初の1回の観察から「このモデルは指示を無視する」とは言えなかった、ということです。

緩い指示(baseの「3〜5個」)は、どのモデルでも通ります。厳しい指示(文字数、枚数、書式)は、モデルによって、どの要素を落とすかが違います。そして、モデルの大きさや新しさでは並べられませんでした。4Bが通り、9Bが通らず、27Bが枚数を無視する、という結果は、使うモデルごとに実際に試す必要があることを示しています。

実務での使い方として言えるのは次の3点です。

- 形式を守らせたいなら、「3個」「80字以内」のような検査できる条件にして、出力を機械的に数えるのが確実
- 守れない項目(文字数など)は、モデルによって違うので、使うモデルで一度は試す
- 思考を止められないモデル(LFM2.5)は、生成の上限を余裕を持って指定する

## この結論が変わりうる条件

- 各条件は3回で、同じ入力の記事は1つだけ。別の文書では結果が変わる可能性がある
- 判定は形式の機械的な数え上げだけで、要約の内容の正確さ・過不足は見ていない
- 元の測定と今回の測定は、温度やモデルの取得元が揃っていない。食い違いの原因は特定していない
- Ornith系、Bonsai 2などは、今回の3プロンプトでは測っていない
