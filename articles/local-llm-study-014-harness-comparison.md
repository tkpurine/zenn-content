> **結論**: Qwen3.5 9B を同じ llama-server に載せ、Codex CLI・Claude Code・Copilot CLI だけを替えて測ると、バグ修正（study2）や易しいファイル操作は3つとも全部成功して差が出なかった。差が出たのは、コンテキスト長（32k と 64k）と、ツールの結果の見え方（並列 Read の順序、Read の行番号）だった。ハーネス間の優劣は n=2 では断定できない。Copilot CLI に指示ファイルを足して SVD などの失敗を減らそうとしたが、改善しなかった。
>
> **読者が得るもの**: ローカルLLMで複数のコーディングエージェントを同じ条件で並べるときの接続の手順と、結果を読むときに先に確認すべき点（コンテキスト長、ツールの結果がモデルにどう見えるか、ターン上限の有無）が分かる。あわせて、指示ファイルだけでは小さいモデルの「修正のループ」が直らなかった実測も分かる。

## この記事について

study12・study13 では、Qwen Code というひとつのハーネスに、モデルを替えて測りました。この記事は逆に、**モデルを1つに固定して、ハーネスだけを替えます**。使うのは Codex CLI、Claude Code、GitHub Copilot CLI の3つです。3つとも、ローカルの llama-server に直接つないで動かしました。

先に断っておくと、成功数の差は n=2 の範囲です。優劣をつけるための記事ではなく、「同じモデルでも、ハーネス側の事情で結果がこれだけ動く」ことと、その原因を切り分けた記録として読んでください。

## 検証の条件

- **モデル**: Qwen3.5 9B（unsloth の Q4_K_M）。小さいモデルを選んだのは、3ハーネス×複数タスク×32k・64kの2条件を、16GBのMac miniで数時間のうちに回すためです
- **サーバー**: llama-server（bonsai-demo の b10782）を1つだけ起動し、3つのハーネスで共用。コンテキスト長は `-c 32768` と `-c 65536` の2通り。推論の設定はサーバーの既定のままです
- **ハーネスのバージョン**: Codex CLI 0.166.0、Claude Code 2.1.303、GitHub Copilot CLI 1.0.105
- **条件**: 条件A（1つの指示で直接実装）だけ。各タスク n=2
- **壁時間**: コード系は1回30分、ファイル操作系の新タスクは15分、外部ベンチマークのタスクは10分で、外から強制終了します。壁時間切れは失敗として数えました
- **権限**: 作業ディレクトリ内の読み書きと、python・ls・cat の実行だけを許可しました。権限をすべて外す設定は使っていません

接続の方法は次のとおりです。どれも、環境変数や引数で llama-server を指すだけで動きました。

| ハーネス | 使うAPI | 指定の要点 |
|---|---|---|
| Codex CLI | `/v1/responses` | `-c` で `model_providers` を定義し、`wire_api="responses"`。`model_context_window` と自動圧縮の閾値を渡す |
| Claude Code | `/v1/messages` | `ANTHROPIC_BASE_URL`（`/v1` は付けない）と各モデル名の環境変数。`CLAUDE_CODE_MAX_CONTEXT_TOKENS` で窓を渡す |
| Copilot CLI | `/v1/chat/completions` | `COPILOT_OFFLINE=true` と BYOK の環境変数。GitHub の課金枠は使わない |

Codex だけ、そのままでは動きませんでした。Codex は会話の途中にも system メッセージを入れますが、Qwen3.5 のチャットテンプレートは「system は先頭に1つだけ」と決めていて、llama-server が HTTP 500 を返します。テンプレートの該当する1行を、例外を出さずにそのまま出力する形に書き換えて解決しました。公平のため、**3ハーネスすべてでこの書き換え後のテンプレートを使っています**。

使ったタスクは、study12 と同じバグ修正（study2）、カルマンフィルタ、SVD です。判定も同じで、テストが通ること、必須のテストが実際に assert を含むこと（SVD はさらに検証スクリプトに通ること）を機械で確認します。

## 結果1: コード系のタスク

次の表は、成功数と、括弧内の所要秒です。コンテキスト長を32kと64kで分けています。study2 は易しいので32kだけ測りました。

| ハーネス | コンテキスト | study2 | カルマン | SVD |
|---|---|---|---|---|
| Codex | 32k | 2/2（63・49） | 2/2（1132・915） | 0/2（1017、壁時間切れ） |
| Codex | 64k | — | 2/2（622・149） | 1/2（685で成功、770で失敗） |
| Claude Code | 32k | 2/2（214・82） | 無効（2回とも後述のエラー） | 1/2（298で成功、363は後述のエラー） |
| Claude Code | 64k | — | 2/2（528・152） | 2/2（1360・1171） |
| Copilot CLI | 32k | 2/2（82・77） | 1/2（258で成功、557で失敗） | 0/2（564・531） |
| Copilot CLI | 64k | — | 2/2（307・263） | 0/2（2回とも壁時間切れ） |

この表で見てほしいのは、横（ハーネス）の差より、**同じ行の32kから64kへの変化**です。Codex の SVD は0/2から1/2、Copilot CLI のカルマンは1/2から2/2、Claude Code は無効だったカルマンと1/2だった SVD がどちらも2/2になっています。逆に悪化した組み合わせは、この表にはありません。ただし n=2 なので、1回の成否で動く範囲です。

study2 は3ハーネスとも6回中6回成功で、所要時間も49〜214秒に収まります。これだけでは差を分けられないため、カルマンと SVD を主な比較対象にしました。

### Claude Code の「無効」の中身

Claude Code の32kでは、カルマン2回と SVD の1回が、同じエラーで終わりました。「自動圧縮が連続して失敗した（コンテキストが圧縮の直後にまた満杯になる）」という内容です。モデルの出した答えの良し悪しではなく、**ハーネスがコンテキストを管理しきれずに止まった**状態です。

これは、Claude Code が毎回送る固定のシステムプロンプトとツール定義が大きく、32kでは作業用の余白が足りないためだと考えています。この説明は、64kに広げると4回すべてで同じエラーが出なくなったことから推測したものです。Claude Code の内部を読んで確かめたわけではありません。そのため、32kの Claude Code の失敗は成功率に含めず、「無効」と書きました。

### 失敗の中身は一様ではない

0/2の行でも、中身は違います。Codex の32k SVD は、1回が1017秒で自分のテストが通らないまま終了し、もう1回が壁時間（1800秒）で打ち切られました。Copilot CLI の64k SVD は、2回とも壁時間切れで、ツール呼び出しはそれぞれ41回と35回に達していました。長く動いても収束しなかったと読めますが、途中の挙動までは追っていません。

## 結果2: ファイル操作・文書作成に近いタスク

コード系だけだと、ハーネスの差が出にくい恐れがありました。そこで、ファイル操作に近い3タスクを、各1パターンだけ追加しました。判定はすべて機械で行い、LLM による採点は使っていません。

- **organize**: 大文字小文字が混ざった8ファイルを、拡張子ごとのフォルダ（txt・csv・md・py）に移し、名前を小文字にする
- **extract**: 3つのファイル（csv 2つとテキスト 1つ）から地域別の売上合計を出して、summary.csv に書く
- **slides**: outline.md から、5枚の Markdown スライドを作る。枚数、見出し、最後が「まとめ」であること、指定の数字が入っていることを確認する

次の表は、成功数です。左が32k、右が64kです。

| ハーネス | organize | extract | slides |
|---|---|---|---|
| Codex | 1/2・1/2 | 2/2・1/2 | 2/2・2/2 |
| Claude Code | 2/2・1/2 | 0/2・0/2 | 2/2・2/2 |
| Copilot CLI | 0/2・1/2 | 2/2・2/2 | 2/2・2/2 |

slides は6条件すべて全部成功で、このタスクでは差が出ませんでした。所要も30〜150秒です。

organize の失敗は、読み取れる限り2種類でした。ひとつは、フォルダには分けたのに、名前を小文字にし損ねるものです（Budget.CSV だけ大文字のまま、という近い失敗が Claude Code と Codex で1回ずつ）。もうひとつは、ファイルをフォルダ直下に残すなど、移動が終わっていないものです（Copilot CLI で3回）。Codex の32kの1回は、フォルダ分けだけで小文字化をしていませんでした。ハーネスごとの傾向と呼べる数ではなく、**小さいモデルが指示の「全部」を取りこぼす**失敗が、ハーネスにまたがって出たと見るのが妥当です。

### extract で Claude Code が0/2になった理由

extract は、Claude Code だけが32k・64kとも0/2で、他の2つは8回中7回成功でした。失敗した4回の出力を見ると、合計値は3つとも正しく計算されていて、**地域の名前が入れ替わっていました**。正解は north=40000、south=34900、east=24000 ですが、たとえば north に 24000 を書いています。

ログを読むと、モデルは3つのファイルを同時に読みます。ところが、返ってくる結果の順番は毎回違い、結果にファイル名が付いていません。モデルは、返ってきた順番を、読み込みを頼んだ順番だと思い込んで名前を当てていました。

最初は、プロンプトの書き順（north・south・east）とファイル一覧の順（アルファベット順）のずれが原因だと予測しました。これを確かめるため、データはそのままに、プロンプトの列挙順をアルファベット順（east・north・south）にした版を追加し、Claude Code の64kで4回測りました。結果は1/4で、**予測は外れ**でした。ログでは、この版でも結果の返る順は毎回ばらばらで、失敗した3回は同じ入れ替わりを起こしています。成功した1回だけ、モデルが自分で `cat` を使い、ファイル名付きの出力で確かめ直していました。

したがって、原因は列挙順の食い違いではなく、並列に読んだ結果の順序が不定で、結果にファイル名がないことでした。Codex と Copilot CLI のログも確認しました。両方とも、ファイルを読むときにシェルを1回だけ呼び、`head -5 north.csv south.csv east.txt` のようにファイル名を引数に並べています。この出力には `==> north.csv <==` というファイル名の見出しが付くか、`cat` の引数順にそのまま連結されるので、順序が入れ替わる余地がありません。そのうえ、合計を出す Python のコードの中でファイル名を直接指定して読んでいました。Copilot CLI は4回とも、ほぼ同じ手順（`head`、集計のシェル、Python、`cat summary.csv` での確認）でした。これが、取り違えが起きにくかった理由だと考えられます。なお Codex の64kの失敗1回は取り違えではなく、計算のミスでした（north=98900 は3地域の合計に一致していて、値が混ざっています）。

## 結果3: 複数ファイルの作業と、長いログの読み取り

ファイル操作の次に、実際の作業に近い3タスクを足しました。やはり機械で判定します。

- **refactor**: 4ファイルの小さな在庫管理アプリで、変数名 `qty` を `quantity` に全ファイルで変える。テストが通ること、テストファイルを変えないこと、`qty` が残らないことを確認する
- **longdoc**: 500行のログから、種類別のエラー件数、ディスク満杯の時刻、最も遅いリクエストの ID を答え、answer.json に書く
- **messy**: カンマ区切り、括弧つきの負数、N/A、空欄など、書式がばらばらな6ファイルの数値を合計し、totals.json に書く

次の表は成功数です。左が32k、右が64kです。

| ハーネス | refactor | longdoc | messy |
|---|---|---|---|
| Codex | 2/2・2/2 | 2/2・2/2 | 1/2・2/2 |
| Claude Code | 0/2・2/2 | 0/2・1/2 | 1/2・0/2 |
| Copilot CLI | 2/2・2/2 | 0/2・1/2 | 2/2・2/2 |

Claude Code の32kで refactor と longdoc が0/2なのは、固定プロンプトでコンテキストが足りない影響の可能性があります。ただし、今回はこの2つのログで自動圧縮の失敗を確かめていません。messy の Claude Code 64k（0/2）は、合計値の組が名前とずれる、extract と似た間違いでした（alpha に epsilon の値が入るなど）。同じ原因かどうかは、ログで確かめていません。Codex は6条件中5条件で2/2でした。

## 結果4: 外部ベンチマークの10タスク

ここまでのタスクは自作で、偏りがあります。そこで、公開されているベンチマーク harness-bench-fast（PyPI の 0.1.0）から、種類の違う10タスクを選びました。関数名の変更、数値の合計、CSV の結合、SQLite の集計、バグ修正、ログの集計、複数ファイルの名前変更、バージョン文字列の解析、ステータスの行列の作成、マージ競合の解消です。判定はベンチマークの検証コードをそのまま使っています。

このベンチマークのプロンプトは原文がロシア語です。最初はそのまま測りましたが、実際の使い方と違う可能性があるため、**プロンプトだけを日本語に訳して**測り直しました。ファイルや判定は同じです。

**言語を替えても、全体の成功数はほとんど変わりませんでした。** 差は最大でも2回(Claude Code の32k)で、n=2 では誤差の範囲です。ロシア語で測った結果を、日本語の利用にそのまま当てはめても、大きくは外れない、というのが今回の結論です。タスク単位では、Claude Code の sum_numbers と、Codex の terminal_log_status_matrix(64k)が目立って動きました。

これは extract と同じ種類の問題です。モデルの計算力ではなく、**ツールの結果がモデルにどう見えるか**で結果が決まっています。

## 結果5: Copilot CLI に指示ファイルを足すと改善するか

ここまでで、Copilot CLI の SVD は4回中3回が壁時間切れでした（64k、n=4に増やして1/4）。ログでは、モデルが自分で書いたテストの中で `np.linalg.svd` の戻り値の順序を取り違え、そのテストが通らないまま実装を直し続けていました。そこで、**一般的な作業ルールだけを書いた指示ファイル**（AGENTS.md の形）を Copilot CLI に読ませ、改善するかを64kで測りました。

指示ファイルの内容は、SVD の答えを含めません。次のような一般論です。

- 複数のファイルは、取り違えないように1つずつ、またはファイル名つきで読む
- 「すべて」と書かれたら、対象を書き出し、最後に1つずつ確認する
- テストが落ちたら、実装だけでなく、テストの期待値やライブラリの戻り値の形も疑い、小さな確認コードで確かめる
- 同じ種類の修正が3回続けて直らなければ、前提を疑って確かめ直す
- 完了の前に、成果物ができていることを確かめる

指示ファイルが読み込まれていることは、実行のセッション記録で確認しました（システムメッセージに内容が入っています）。このルールは SVD や extract の失敗から作ったため、調整に使ったタスクだけで測ると過学習を見分けられません。そこで、使っていないタスクも合わせて測りました。

| タスク | 指示なし | 指示あり |
|---|---|---|
| カルマン（n=4） | 3/4 | 2/4 |
| SVD（n=4） | 1/4 | 0/4 |
| organize（n=4） | 1/4 | 0/4 |
| longdoc（n=2） | 1/2 | 1/2 |
| messy・refactor・slides（n=2） | 2/2 | 2/2 |
| extract（n=2） | 2/2 | 1/2 |
| 外部ベンチマーク10タスク（n=2） | 8タスクが2/2、2タスクが1/2 | 同じ（全タスクで一致） |

**指示ファイルでは改善しませんでした。** 調整に使ったタスクは、n=4 で有意とは言えないものの、むしろ悪い数字です。使っていないタスクは、ほぼ同じ結果でした。失敗の形も変わらず、SVD は壁時間切れ、organize は900秒までツールを146回呼ぶ回がありました。「3回直らなければ前提を疑う」というルールを入れても、実際の行動は変わりませんでした。

見立てとしては、小さいモデルの失敗は「ルールを知らない」ことより、修正のループに入ること自体から来ているのかもしれません。ただし、これは確かめていません。ルールを文章で渡す方法を1種類、1つの文面で試しただけで、出力トークン数の設定、スキル、フックのような別の手段は未検証です。

## 公平性についての注意

- **ターン上限**: Claude Code だけ `--max-turns 40` を付けました。Codex と Copilot CLI にはターンの上限がなく、壁時間だけで止まります。今回は、ターン上限に当たって止まった実行はありませんでした。
- **コンテキストの渡し方**: Codex と Claude Code にはコンテキスト窓の大きさと自動圧縮の閾値を渡しましたが、ハーネスごとに仕組みが違い、同じ意味ではありません。
- **トークン数**: Codex は1ターンの累積値、Claude Code は出力トークンが取れず0、Copilot CLI は解析していません。トークン数は比較に使えないため、表には載せていません。
- **測定の時期**: 64kの Claude Code と、Codex・Copilot CLI の64kは、別の日の別セッションで測っています。
- **メモリ**: 測定中のメモリ圧迫は最大でも「警告」の段階で、スワップは3〜10GBでした。`llama-server` 自体のメモリは9.5〜9.9GBで安定していました。スワップが増えた原因は特定できていません。

## 考察

表の実測値から言えることだけを書きます。

**このモデルとこのタスクでは、ハーネスの差より、コンテキスト長の差のほうが目立ちました。** 32kから64kに広げると、改善した組み合わせが4つ（Codex の SVD、Copilot CLI のカルマン、Claude Code のカルマンと SVD）あり、悪化した組み合わせはコード系にありませんでした。コンテキスト窓は、ハーネスの固定プロンプトの大きさと合わせて効く、見落としやすい条件です。

**ハーネスの優劣は、n=2 では決められません。** たとえば64kの SVD は、Claude Code 2/2、Codex 1/2、Copilot CLI 0/2ですが、1回の成否で順位が変わる数です。Copilot CLI の SVD は2回とも壁時間切れなので、時間をもっと与えれば結果が変わる可能性もあります。

**ハーネスの「道具の癖」が、タスクによっては結果を左右します。** extract の取り違えは、モデルの計算力ではなく、並列読み込みの結果の返り方と、それを見直すかどうかで決まっていました。ハーネスの比較では、モデルの出力だけでなく、ツールの結果がモデルにどう見えているかも確認する必要があります。

**ツールの結果の見え方は、Claude Code で2回効きました。** extract では並列 Read の結果順が不定でファイル名がなく、sum_numbers(ロシア語版)では Read の行番号を数として足しました。どちらも、モデルの計算力ではなくハーネスの出力の形が原因です。ただし、Codex と Copilot CLI にも別の弱点があり、たとえば Codex は fix_bug で、バグが直らないまま終えた回がありました。

**指示ファイルは、このモデルの修正のループを止めませんでした。** 一般的な作業ルールを AGENTS.md の形で渡しても、Copilot CLI の SVD や organize は改善しませんでした。「ハーネスの設定を整えれば、強いハーネスに近づく」という期待は、この方法ではまだ裏づけられていません。

## この結論が変わりうる条件

- 各条件 n=2（検証の extract_alpha だけ n=4）で、成功率は測れていません。1回の成否で順位が入れ替わります
- モデルは Qwen3.5 9B の1つだけです。大きいモデルでは、ハーネス間の差の出方が変わる可能性があります
- 条件Aだけで、plan mode などハーネス固有の機能は使っていません
- 64kの測定は、32kとは別のセッションで行っています。サーバーを起動し直しており、メモリの状態も違います
- Codex と Copilot CLI の extract は、それぞれ4本のログの読み方を確認しただけで、取り違えが起きにくい理由を因果として証明したものではありません
- 新タスクは各1パターンで、問題の作り方に偏りがあります。slides は易しすぎて差が出ませんでした
- 外部ベンチマークの10タスクは、原文のロシア語と、私が訳した日本語の両方で測りました。訳文の質が結果に影響している可能性は検証していません
- 外部ベンチマークは、全体のごく一部の10タスクだけを選んでいます
- 指示ファイルは1つの文面だけを試しました。調整用のタスクは n=4、確認用は n=2 で、指示なしの基準も、一部は別の時期に測っています
- Claude Code の sum_numbers の原因は、ログを読んで特定しましたが、他の Claude Code の失敗（messy、32kの refactor と longdoc）は原因を確かめていません
- 実行環境は Apple Silicon の Mac mini（メモリ16GB）です。所要時間は、メモリ圧迫の影響を含みます
