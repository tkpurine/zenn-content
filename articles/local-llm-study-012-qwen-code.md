## この記事について

Qwen Code（QwenLM/qwen-code、v0.26.0）を、これまで比較してきたローカルLLM 5つで動かし、固定タスクの成否と所要時間を測りました。Qwen Code には読み取り専用の plan mode があるので、「計画してから実装する」ことで成績が変わるかも見ています。

結論を先に書くと、**単純なバグ修正はほぼ全モデルが成功し、カルマンフィルタとSVDの実装は、条件Cを含む52回のうち7回しか成功しませんでした**。ただし、その52回のうち19回は壁時間（30分など）で打ち切られて結果が出ておらず、特に27B級の2モデルは、カルマンとSVDのほとんどが「測定不能」です。plan mode の効果は、n=2 では「ある」とも「ない」とも言えません。

もう一つ分かったのは、Qwen3.8-27B は**推論（thinking）をオフにすると、同じ壁時間のまま、カルマンとSVDの成功が大きく増えた**ことです。推論オン・30分では8回すべてが壁時間切れで測定不能でしたが、推論オフ（n=5に増やした測定）では、カルマンとSVDの20回のうち16回が成功しました。27B級の「測定不能」は、モデルの実装力ではなく、推論の長さの問題だった可能性が高いです。壁時間を伸ばした実験は、別の記事にまとめます。

## 検証方法

- **ツール**: Qwen Code 0.26.0 を `llm-lab/.tools/` にローカルインストール。`~/.qwen` を汚さないよう、実行ごとに HOME を隔離し、`--bare` で実行
- **接続**: llama-server（OpenAI互換、`-c 32768`）に `OPENAI_BASE_URL` で接続。1モデルずつロードし、同時にロードしない
- **タスク**（`llm-lab/tasks/qwencode/` に凍結）: ①study2のAiderと同じ境界値バグ修正、②monocoderと同じカルマンフィルタ、③同じくべき乗法SVD。各 n=2
- **条件**:
  - **A**: `--approval-mode yolo` で直接実装
  - **B**: まず `--approval-mode plan` で計画だけを出させ（編集とシェルは実行されない）、その計画を渡して `yolo` で実装
  - **C**: 実装は小型3モデル、計画は Qwen3.8-27B が B で出したもの
- **成功の判定**: バグ修正はテストが通り、テストファイルのハッシュが不変で、`calc.py` が変わっていること。カルマン／SVDは、モデル自身が書いたテストが通り、monocoder と同じガード（必須テスト名の存在、assert の存在、実装の import）を満たすこと。SVDはこれに加えて、モデルのテストに依存しない独立検証（`verify_svd.py`）も通ること
- **予算**: 1回の呼び出しは壁時間（2B:10分、4B:15分、9B:20分、27B:30分）と最大40ターンで打ち切り。サーバー／接続エラーとは分けて記録
- **打ち切りの数え方**: 40ターンで止まった実行は、収束しなかったモデル側の失敗として成功率の分母に入れます。壁時間で打ち切られた実行は、モデルが答えを出せたかが分からないため分母に入れず、「壁時間切れ」として別に数えます。同じ条件の2回とも壁時間切れなら「測定不能」と書きます

## 考察

表の実測値から言えることだけを書きます。いずれも n=2 です。

**単純なバグ修正は、2B 以外ほぼ全員が成功しました。** 差は時間に出ています。A の平均は 9B が36秒、4B が28秒、Bonsai 2 27B が108秒、Qwen3.8-27B が254秒でした。

**カルマンとSVDは、このサイズのローカルモデルには厳しい課題でした。** A と B を合わせた40回のうち、成功は4回です。ただし18回は壁時間で打ち切られて結果が出ておらず、自力で終了した22回に限っても成功は4回でした。

**27B級の2モデルは、カルマンとSVDの大半が「測定不能」です。** Qwen3.8-27B は、カルマン・SVD の A/B 8回がすべて壁時間切れで、そのうち6回はツール呼び出しが1回も完了していません。Bonsai 2 27B も8回のうち6回が壁時間切れでした。表の成功数は、この2モデルの実装力を表していません。

**plan mode の効果は、この件数では判断できません。** 自力で終了した実行に限ると、カルマンとSVDの成功は、A が1/10、B が3/12（Bonsai 2 27B が2回、4B が1回）で、差は2回分です。9B のカルマンは A が1成功、B が0成功と逆でした（どちらも壁時間切れが1回ずつ含まれます）。一方、時間はほぼ確実に増えます。バグ修正で A→B の平均は、9B が36→61秒、4B が28→35秒、Bonsai 2 27B が108→302秒、Qwen3.8-27B が254→645秒でした。

**27Bの計画で小型が実装する C は、カルマンで 4B が B の1/2のまま、9B が1/2でした。** 小型3モデルのカルマンは、A が1/6、B が1/6、C が2/6です。SVD は、A が0/6、B が0/6、C が1/6（4B の1回）でした（分母は実行数です）。C が最も高いものの、差は1回分ずつです。

**SVDは、実装が正しくても失敗扱いになる実行が目立ちました。** 独立検証は通ったのに失敗とした実行が8回あります（9B が5回、4B が2回、Bonsai 2 27B が1回）。うち6回は、モデルが自分のテストを直し続けて予算切れになった実行です。1回（4B の A run1）は、予算内で止まったものの自分のテストが通らないままでした。残る1回（9B の A run2）は、必須の4テストのうち3つが消えた状態でテストが全部通っていました。実装そのものの正しさと、テストを書いて通す工程の失敗は、分けて見る必要があります。

**小型モデルでは、ツール形式の崩れによる再試行がありました。** Qwen Code が「破棄してやり直す」再試行は、2B が21回、9B が23回、4B が13回、Bonsai 2 27B が9回、Qwen3.8-27B が7回でした。2B の svd B run2 は、計画フェーズのツール呼び出しが1000回と記録された暴走でした。

**Qwen3.8-27B は、推論をオフにすると、カルマンとSVDの成功が大きく増えました。** 推論オンでは壁時間切れで測定不能だったカルマンとSVDも、n=5で測り直すと、A/B の計20回のうち16回が成功しています（カルマン A 4/5、B 4/5、SVD A 4/5、B 4/5。失敗4回のうち壁時間切れが3回、ターン上限が1回。成功した16回の所要時間は8〜35分）。バグ修正は A/B とも5/5でした。ログを数えると、推論オフの45本には推論ブロックが0件で、推論オンの18本には63件（合計約30万字）あり、推論が実際に無効だったことは確認できています。同じモデル・同じ壁時間・同じコンテキストで結果が変わったので、27B級の遅さは、メモリ圧迫よりも推論の長さの影響が大きかった可能性が高いです。ただし、推論オフの測定は Qwen3.8-27B だけで、Bonsai 2 27B や小型モデルでは測っていません。

## まとめ

| 観点 | 実測（n=2） |
|---|---|
| バグ修正（2B以外） | A・B・C ともほぼ全成功 |
| カルマン・SVD（A+B 40回、C込みで52回） | 成功4回（C込みで7回）。うち壁時間切れは18回（C込みで19回） |
| 27B級2モデルのカルマン・SVD | 大半が壁時間切れで測定不能。成功数は実装力を表さない |
| plan mode の効果 | 自力で終了した実行で A 1/10 → B 3/12。差は2回分で判断不能。時間は増える |
| 27Bの計画で小型が実装（C） | カルマンで小型3モデル合計 1/6（A）→ 2/6（C）、SVD で 0/6 → 1/6。差は1回分ずつ |
| Qwen3.8-27B の推論オフ（別測定、n=5） | カルマン・SVD の20回のうち16回が成功。壁時間切れの主因は推論の長さだった可能性が高い |

Qwen Code でローカルLLMを動かす場合、単純な修正なら小型モデルでも数十秒で終わる一方、複数ファイルの実装とテストの両方を求めると、小型モデルはほとんどの実行が予算切れか、テストの不整合で終わりました。27B級は、推論をオンのまま30分で測ると、そもそも結果が出ない実行が大半でした。

## この結論が変わりうる条件

- 各条件 n=2 で、成功率は測れていません。「差がある」とも「ない」とも言えない箇所が多くあります
- **Qwen3.8-27B は Thinking が有効のまま動いていました。** 過去の study は `think:false` で測っているので、条件が違います。kalman と svd の A（4回）はツール呼び出しが1回も完了せず、ログを読んだ kalman A run1 と svd A run1 では、30分間に約1.6万字の推論を2本出して止まっていました。Qwen3.8-27B の kalman／svd の「測定不能」は、モデルの実装力ではなく、推論の長さと速度の問題でした（推論オフの再測定は上の表のとおり20回中16回成功）。ただし、再測定は Qwen3.8-27B のみで、サーバーの設定は別セッションで行われたものです。Bonsai 2 27B は推論をオンのまま測っています
- メモリ16GBでは、27B 級の実行中にスワップがほぼ満杯になりました（14.3GB 中 13.5GB 使用）。27B の所要時間はメモリ圧迫の影響を含みます
- 打ち切りは壁時間とターン数の上限で決めており、上限を伸ばせば成功した実行があるかもしれません。壁時間切れを成功率の分母から外したため、「自力で終了した実行」だけで比べており、モデルによって分母の大きさが違います。モデルごとに壁時間も変えているので、所要時間をモデル間で直接比べるのは慎重にしてください。壁時間を90分に伸ばした実験は、別の記事で扱います
- **Qwen Code には、壁時間とは別に、1回のストリーミング応答の総待ち時間の上限（`QWEN_STREAM_MAX_LIFETIME_MS`、既定15分）があります。** 本測定ではこれを変えていないため、27B級で1回の推論が15分を超えた場合は、打ち切られて再試行されていた可能性があります。壁時間を90分に伸ばした追加検証の最初の試行では、条件Aの4回がこの上限で約45分（3回×約15分）に終了していました（別の記事で扱います）
- カルマンの判定はモデル自身のテストが通ることが基準で、独立検証はありません。弱いテストで通る場合があります（ガードで必須テスト名と assert の有無は見ています）
- study2 の `calc.py` には、バグの位置を示すコメントが残っています。Aider の過去結果と同じ fixture のため比較はできますが、「バグの場所は教えません」という条件は、実際には守られていません
- 計画の簡体字混入は、保存した29件の計画をスキャンして0件でした。途中で破棄した最初の実行では4Bの計画に簡体字が混じっていたので、混入が起きないとは言えません
- 実行環境は Apple M6、16GB です。他のチップでは所要時間が変わります
