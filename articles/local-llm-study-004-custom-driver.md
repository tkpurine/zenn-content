## この記事について

[study3](https://zenn.dev/) と [study3-a](https://zenn.dev/) を通じて、Aiderの`--edit-format whole`パーサーが「ファイル名とコードフェンスの境界」を誤解釈し、正しく生成されたはずのコードが0バイトファイルやゴミファイルとして失われる事故を繰り返し観測しました。特にstudy3-aでは、`gemma4:e2b-mlx`が検証した2タスクとも初回にこの事故を起こしています。

この失敗はモデルの能力ではなくAiderのパース層の問題に見えたため、「用途を1リクエスト1ファイルに限定した自作ドライバを作れば、この失敗クラスを構造的に消せるのでは」という仮説を立て、実際に作って検証しました。

結論から言うと、**パーサー崩壊は狙い通りゼロにできました**。ただし最初の検証では成功率が6回中1回まで落ち込み、Aiderの過去実績と比べて明確に見劣りする結果になりました。ログを1つずつ調べて6つの要因を特定し、すべて修正した上で再検証したところ、成功率は**6回中5回**まで改善しました。この記事では、パーサー崩壊をゼロにできたという当初の成果に加えて、その後見つかった一連のツール側の欠陥と、実際に効果のあった改善を記録します。

## monocoderの設計

`~/dev/monocoder/`に作った約300行のPythonスクリプト（標準ライブラリのみ）です。

### 当初案からの設計変更：JSON構造化出力はMLXバックエンド非対応

最初は「Ollamaの`format`パラメータでJSON schemaを強制し、ファイル内容をJSON文字列フィールドとして受け取る」設計を考えていました。しかし実装前のスモークテストで、これがMLXバックエンドでは機能しないことが判明しました。

| モデル | バックエンド | `format`によるJSON schema強制 |
|---|---|---|
| gemma4:e2b（通常版） | GGUF | 動作（正しくJSONを返す） |
| qwen2.5-coder:7b | GGUF | 動作 |
| gemma4:e2b-mlx | MLX | **無視され、プレーンテキストで返る** |
| gemma4:e4b-mlx | MLX | **無視され、プレーンテキストで返る** |

Ollamaの構造化出力（grammar制約デコード）はllama.cpp（GGUF）バックエンドの機能で、MLXバックエンドには未実装と見られます。study4の主役はMLX版モデルなので、この設計は使えません。

代わりに、system promptで「生ファイル内容のみ、フェンス・説明・ファイル名見出しなし」を強く指示し、応答をほぼそのままファイルに書く方式に変更しました。念のため先頭/末尾のコードフェンス行だけを除去する防御的な後処理を入れていますが、これはパースの主手段ではなく保険です。スモークテストでは、この指示だけでe2b-mlxが一発でフェンスなしの綺麗なコードを返しました。

### コマンドと内部フロー

- `monocoder gen`: 1プロンプト→1ファイルの単発生成
- `monocoder tdd`: 実装+テストを生成し、`--auto-test`相当の修正ループを回す
- `monocoder pipeline`: 設定ファイル駆動で「計画→実装+テスト→ドキュメント化」の3段階を実行（study3と同じ構成）

`tdd`の内部フローが設計の核心です。

```
1. 実装ファイルを生成
2. テストファイルを生成
   → ガード群（下記）で品質チェック。違反があれば再生成（最大3回）
   → 合格したらSHA256を記録し、以後このテストファイルには二度と触らない
3. test-cmdを実行
4a. PASS → 成功終了
4b. FAIL → 失敗内容を渡し「実装ファイルだけを修正した全文」を要求 → 3へ
5. 規定回数（max-iter）失敗したら、チャット履歴を破棄して新規セッションで再試行
6. それでも失敗 → FAILとして終了（silent failureにしない）
```

### 実装したガード

| ガード | 内容 | 対応する失敗パターン |
|---|---|---|
| G1 | テストファイルのSHA256を生成直後に固定し、以後変化していないか毎ループ確認 | ①テスト改竄 |
| G2 | テストファイルをAST解析し、テストメソッド0件・pass-only本体・assert 0件を検出 | ②空虚な成功 |
| G_empty | test-cmdの出力に`Ran 0 tests`が含まれていないか確認（exit code 0でも偽陽性PASSにしない） | ②空虚な成功（別形態） |
| G3 | tddのfix-loopは実装ファイルしか書き換えない（構造上、テスト改竄・許容誤差の緩和が不可能） | ①③ |
| **G5**（実装中に新規発見） | テストファイルが実装モジュールを実際に`import`しているかAST解析で確認 | 後述 |

G1〜G3は計画段階で想定していたものですが、G5は実装・検証の過程で偶然見つけた失敗パターンへの対策として追加しました。

## G5：計画になかった新しい失敗パターン

SVDタスクの`tdd`を最初に走らせたとき、実装(`svd.py`)をいくら正しく修正してもテストが同じ理由で失敗し続けるという事象に遭遇しました。テストのトレースバックをよく見ると、おかしな点がありました。

```
File "/private/tmp/monocoder_svd_test/test_svd.py", line 27, in power_iteration_svd
```

`power_iteration_svd`関数が`svd.py`ではなく**`test_svd.py`自身の中で定義されている**ことを示しています。テストプロンプトが「svd.pyのpower_iteration_svd関数をテストしてください」という関数の**振る舞いの説明**だけを渡しており、実際のsvd.pyの中身を見せていなかったため、モデルは`from svd import power_iteration_svd`とインポートする代わりに、**自分で（しかも同じ欠陥のあるアルゴリズムで）関数を再実装してテストファイルに埋め込んで**いました。実装側をいくら直しても、テストが見ているのは常にこの埋め込みコピーだったわけです。

これはAiderでは起こり得ない失敗です。Aiderは会話履歴の中に実装ファイルの中身が常に見えているため、こんな独立した再実装は起きません。monocoderが「1リクエスト1ファイル」を徹底し、各生成をなるべく独立させた設計上のトレードオフが生んだ、**自作ならではの新しい失敗パターン**でした。

対策として、テストファイル生成時のsystem promptに「必ず実装モジュールからimportすること、再実装しないこと」を明記し、AST解析で実際にimport文があるか検証するガード（G5）を追加しました。導入後は同じタスクが一発成功しています。

## 検証方法

study3・study3-aと全く同じ2タスク（カルマンフィルタ、SVDのランク1近似）・同じ指示文を、`gemma4:e2b-mlx`・`gemma4:e4b-mlx`・`ornith:9b`（Ollama公式ライブラリ版）の3モデルで実行しました。

| 項目 | 内容 |
|---|---|
| 実行環境 | monocoder（自作） + Ollama v0.31.2 |
| 端末 | Apple M4 / 16GB統合メモリ |
| tdd設定 | `max-iter: 3`, `max-session-resets: 1`（最大6回の生成試行） |

## 1回目の検証：成功率6回中1回

上記の設計で最初にフル検証を行ったところ、パーサー崩壊は狙い通り0件でしたが、成功したのは6組中1組だけでした。特にornith:9bはカルマンフィルタに約100分、SVDに約4.6時間かかった末に両方ともFAILしました。「Aiderの実績（study3では386秒で成功）と違いすぎる」という指摘を受けて再検証したところ、これは**monocoder自体のバグ**でした。

問題のプロンプトをOllama APIに直接投げ、パラメータを1つずつ変えて切り分けたところ、`num_predict`（生成上限）を指定しても、Ornith-1.0-9Bはその上限をすべて`message.thinking`（思考過程）の出力に使い切り、`message.content`（実際の回答）を一切生成しないケースがあることが分かりました。`think: false`で思考そのものを無効化すると、同じプロンプトが53秒で正常な内容を返しました。

この発見をきっかけに、他の失敗ケースのログも1つずつ見直し、ornith:9bの速度問題以外にも5つのツール側の欠陥が見つかりました。

## 見つかった6つの要因とすべての修正

| # | 要因 | 根拠 | 修正 |
|---|---|---|---|
| A | fix-loopがテストファイルの中身をモデルに見せず、unittestのエラー出力だけで実装のインターフェース（引数名・型・戻り値の形）を推測させていた | 修正前の失敗の大半がインターフェース不一致系（例：ornith:9bカルマンの`TypeError: object of type 'float' has no len()`） | fixを依頼するプロンプトにテスト全文を含める |
| B | `think`未指定でOrnith-1.0-9Bが特定プロンプトの思考に生成上限を使い切り、回答本体を一切生成しないことがある | 条件を1つずつ変えた再現テストで確認（`think:false`で53秒→正常応答） | `think: false` + 保険の`num_predict: 4096`を追加 |
| C | session resetで実装だけ再生成し、旧テストをpinしたままにしていたため、新旧の関数シグネチャが食い違う | e2b-mlxのSVDで実測（新実装が3引数、pin済みテストは1引数で呼び出し） | resetではテストも実装と対で再生成・再pin |
| D | フェンス除去が応答の先頭/末尾のみで、ファイル中間に紛れ込んだ```を見逃す | svd.py 154行目でSyntaxError | .pyファイルはast.parseで検証し、失敗時のみフェンス行除去を試す |
| E | テストプロンプトに実装の全文を見せると、モデルが「同じファイル内で使える」と誤解し、importをコメントアウトする | 3世代連続で同じ誤りを観測 | system promptに「参照用であり、このファイルでは使えない。importを絶対にコメントアウトしない」を明記 |
| F | ガード却下時のリトライが同一プロンプトの再送のみで、temperature 0.1では同じ誤りを繰り返す | 3回連続で同一の違反 | 却下理由をリトライ用プロンプトに追記するフィードバックを追加 |
| G | AST解析（G2）は`import unittest`漏れのような実行時エラーを検出できない | e4b-mlxカルマンで`NameError: name 'unittest' is not defined`が6イテレーション分の試行を浪費 | pin前にサブプロセスで実際にimportするスモークチェック（**G6**）を追加 |

## 2回目の検証：成功率6回中5回

すべての修正を適用し、全6組を再実行しました。

| モデル | タスク | 結果 | 所要時間 |
|---|---|---|---|
| gemma4:e2b-mlx | カルマンフィルタ | FAIL | 231秒 |
| gemma4:e2b-mlx | SVD | **SUCCESS** | 110秒 |
| gemma4:e4b-mlx | カルマンフィルタ | **SUCCESS** | 273秒 |
| gemma4:e4b-mlx | SVD | **SUCCESS** | 325秒 |
| ornith:9b | カルマンフィルタ | **SUCCESS** | 780秒（G5が1回発動、自動解決） |
| ornith:9b | SVD | **SUCCESS** | 669秒（fix-loop3回目で成功） |

パーサー崩壊は今回も0件、**成功率は6回中5回**まで改善しました。すべての成功はテスト内容を独立に読み、`python3 -m unittest`で再実行して確認済みです。

唯一残ったFAIL（e2b-mlx カルマンフィルタ）は、ガードが一度も発火せず、共分散行列の非対角成分が期待値と噛み合わないという純粋な数値計算のズレでした。テストのインポート漏れやフェンス崩壊のようなツール起因の症状ではなく、モデル自身の実装能力の限界に近いと判断しています。

## Aider vs monocoder

| 失敗パターン | Aider（study3/3a） | monocoder（study4） |
|---|---|---|
| ①テスト改竄 | qwen2.5-coder:7bで発生 | 構造的に不可能（テストは生成後pinされ、fix-loopは実装のみ書き換え） |
| ②空虚な成功 | gemma4:e2bで発生 | AST解析＋import実行スモークチェック（G2/G6）＋独立検証で防止 |
| ③存在しないバグの追跡・許容誤差の隠蔽 | qwen3:14b、e4b-mlx（study3-a）で発生 | テスト側は直せない設計のため、同種の問題が起きればFAILとして正直に露見する |
| ④スコープ逸脱・フォーマット崩壊 | Ornith-1.0-9Bで発生（study3） | 該当なし（1リクエスト1ファイルのため） |
| whole形式パーサーの誤爆 | e2b-mlxで2/2タスク発生（study3-a） | 全12回の実行（1回目・2回目とも）で0件 |
| テストが実装をimportせず自己再実装 | 起こり得ない（会話履歴に実装が見えている） | monocoder固有の新しい失敗として発生（G5で対策） |
| 実装/テストの型不整合 | 起こりにくい（Aiderは同一文脈で両方生成） | 独立生成の代償として発生（要因Aで対策） |
| thinkingモデルの生成暴走 | 未観測（Ornithはむしろ最速） | `think`未指定のツールのバグとして発生（要因Bで対策） |

Aiderの過去実績との比較には1点、フェアネス上の注意点があります。study3・study3-aでの「Aiderの成功」には、人間がテストを直接書き直した例（gemma4:e2bのカルマンフィルタ）や、モデルが許容誤差を緩めて偽陽性PASSした例（study3-aのe4b-mlx SVD）が含まれています。monocoderのFAILはそうした偽陽性を許さない設計の結果であり、見かけの成功率だけを単純比較すると実力差を見誤ります。

## 結論

パーサー崩壊を構造的にゼロにするという当初の仮説は、2回の検証を通じて一貫して成り立ちました。一方で、それだけでは「安定して使えるツール」にはならず、実際に安定させるには**ログを地道に読んで要因を1つずつ特定し、修正する**という当たり前の作業が必要でした。見つかった6つの要因のうち半分（A・D・E）は「モデルへの伝え方」の問題、残り半分（B・C・G）は「monocoder自身の実装漏れ」で、どちらも自作ツールを作る上では避けて通れない領域です。

実務的には、

- **whole形式パーサーの誤爆が繰り返し問題になる特定のモデル・タスクにピンポイントで使う**なら、monocoderのような1リクエスト1ファイル設計は有効で、今回の再検証でも成功率5/6まで到達できた
- ただし「動くツールを作る」までの距離は、パーサー問題を解決した時点では終わっておらず、**実際にモデルを繰り返し走らせてログを読む**工程が改善の大部分を占めた
- 検証結果がAiderのような既知の基準と大きく食い違う場合は、まずツール側を疑うべき、という教訓は今回もそのまま当てはまった（ornith:9bの`think`バグがその典型例）

## この結論が変わりうる条件

- 各条件とも再検証は1回ずつで、統計的サンプルはまだ小さい。temperature 0.1でも生成にはrun-to-runのばらつきが残るため、同一条件を複数回実行しないと成功率の再現性は確認できない
- 唯一残ったe2b-mlx カルマンフィルタのFAILについて、根本原因（共分散行列の計算がなぜ期待値とズレたか）はまだ追跡していない
- Aiderとの成功率比較は、上述の通り「Aiderの成功に人間介入や偽陽性が含まれる」というフェアネス上の懸念があり、単純な数字の比較以上の意味づけには注意が必要
