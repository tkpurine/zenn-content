## この記事について

[study1-c](https://zenn.dev/) で、新しく公開された `Ornith-1.5-9B` を単発Q&Aタスクで検証したところ、`Ornith-1.0-9B` より2〜3倍遅く、正確さは同等という結果でした。この記事では同じモデルを、[study2](https://zenn.dev/)（Aiderでの自律バグ修正）・[study3](https://zenn.dev/)（カルマンフィルタ/SVDの3段階タスク）・[study4](https://zenn.dev/)（自作ドライバmonocoder）の手法でさらに深掘りします。

結論を先に言うと、**Ornith-1.5-9Bは「よく考えるが、その考える時間がAiderという道具と相性が悪い」モデル**でした。単純作業は問題なくこなせる一方、自律修正ループを伴う複雑なタスクではAider経由で2.5時間かけても一度も完走できず、monocoder（`think`パラメータを制御できる自作ドライバ）に切り替えて初めてまともに検証できました。

## study2形式：Aiderでの自律バグ修正

study2と同じ境界値バグ（`in_range`関数の`<`と`<=`の取り違え）を、バグの場所を教えずにAiderの`--auto-test`で自律修正させました。

**結果：81秒で1回で解決。バグは正しく修正され、テスト改竄もありませんでした。**

ただしログを見ると、**whole形式パーサーの誤爆（ゴミファイル3つ）が発生していました。**

```
The `calc.py` file has
So the fix is to change `<` to `<=
The test file `test_calc.py` has
```

原因を辿ると、Ornith-1.5の応答には`</think>`タグで区切られた思考過程が含まれており、その**思考の中で**「`calc.py`の中身はこうです：```python...```」という形式でコードを引用していました。Aiderのwhole形式パーサーは応答全体（thinkingを含む）を走査するため、この引用部分もファイル編集指示と誤認してしまったようです。

幸い最終的な結論部分（`</think>`の後）が正しく`calc.py`という見出しで実際の修正コードを示していたため、本物の`calc.py`は正しく上書きされ、機能的には成功しました。しかし、**Ornith-1.5の長い思考が、Ornith-1.0では起きなかったパーサー誤爆のリスクを新たに生んでいる**ことが分かりました。

## study3形式：Aider経由のカルマンフィルタ・SVD ── 完全にFAIL

study3と同じ3段階タスク（計画→実装+テスト→ドキュメント化）をAider経由で実行しようとしましたが、**Stage1（計画）から深刻なパーサー崩壊が発生し、Stage2（実装+テスト）は3回試行して合計2.5時間かけても一度も完走しませんでした。**

### Stage1：PLAN.mdが8個のゴミファイルに分割された

数式を含むMarkdownを生成させたところ、`P_pred = F · P · F^T + Q` のような個々の数式行がそれぞれ独立したゴミファイルとして切り出され、PLAN.md自体は339バイトの断片だけが残りました。チャット履歴をリセットして再試行したところ1個のゴミファイルにまで減りましたが、それでも内容の後半（テスト戦略の章）が丸ごと別ファイルに分割されており、手動でPLAN.mdへマージする必要がありました。

### Stage2：600秒タイムアウトの無限リトライ

実装+テストの生成では、**Aiderのリクエストが毎回タイムアウトし、指数バックオフで延々とリトライを繰り返す**という事態になりました。

```
litellm.APIConnectionError: OllamaException - litellm.Timeout: Connection timed out after 600.0 seconds.
Retrying in 0.5 seconds...
（以下、32秒間隔まで指数的に延びながら繰り返す）
```

study1-cで確認した通り、Ornith-1.5は単発タスクでも思考量が1.0比10〜17倍に増えています。より複雑なStage2のプロンプトでは、この思考がAiderのデフォルトタイムアウト（600秒）を超えて終わらなくなっていると考えられます。

Aiderには`--thinking-tokens`（生成上限）と`--timeout`（タイムアウト延長）というオプションがあり、これで解決できるはずでした。しかし実際に指定すると、

```
Warning: ollama/hf.co/ornith-ai/Ornith-1.5-9B-GGUF does not support 'thinking_tokens', ignoring.
```

**Aiderの内部モデルデータベースがこのHugging Face直取得のモデル識別子を認識しておらず、指定した`--thinking-tokens`が黙って無視されていました。** `--no-check-model-accepts-settings`で強制しても状況は変わらず、`--timeout 300`に短縮した上で15分間監視しても一切進展がなかったため、そこで打ち切りました。

**study3形式（Aider経由）は、この時点で明確なFAILと判断しました。** SVDタスクも同じ壁にぶつかることが予想されたため、Aiderでの追試は行わず、monocoder（study4）に切り替えました。

## study4形式：monocoder経由 ── 1勝1敗、加えて新しいツールのバグを発見

study4で確立した`think: false`の修正により、monocoder経由ではAiderのようなタイムアウト地獄は発生しませんでした。

| タスク | 結果 | 所要時間 |
|---|---|---|
| カルマンフィルタ | FAIL | 563秒（約9分） |
| SVD | **SUCCESS** | 533秒（約9分、1回の修正で成功） |

パーサー崩壊は今回も発生しませんでした（monocoderの1リクエスト1ファイル設計は、Ornith-1.5のような長い思考を持つモデルに対しても有効に機能しています）。

### カルマンフィルタのFAIL：純粋な実装バグ

ガードは一度も発火せず、`predict(u=0)`のようにスカラーのデフォルト引数を渡した際に`B @ u`（行列×スカラー）で次元エラーが発生するという、Ornith-1.5自身の実装ミスでした。6回の修正試行でも解決できませんでした。

### SVDタスクで見つけた新しいツールのバグ：G6ガードのバイトコードキャッシュ問題

SVDタスクの初回実行では、テストファイルが3回連続で「SyntaxError」としてガード（G6：pin前のimport実行スモークチェック）に却下され、FAILしました。しかし実際に生成されたコードを個別に構文チェックすると**正常にパースできる**という矛盾が見つかりました。

調査したところ、G6ガードが一時ファイル`_g6_probe.py`をサブプロセスでimportして検証する仕組みになっており、**Pythonが生成した`__pycache__/_g6_probe.cpython-39.pyc`が複数回の試行をまたいで残り続け、古いバイトコードキャッシュが再利用されていた**ことが原因でした。同一ディレクトリで同名ファイルを短時間に何度も書き換えてimportする、というG6特有の使い方が引き起こした、**monocoder自身の新しいバグ**です。

`python3 -B`（バイトコードキャッシュ無効化）を追加して修正し、再実行したところSVDタスクはSUCCESSしました。study4で見つけたG5に続き、Ornith-1.5の検証を通じてまた1つ、monocoderの改善点が見つかった形です。

## まとめ

| 検証手法 | 結果 | 所要時間 | 主な発見 |
|---|---|---|---|
| study1形式（単発Q&A） | 内容は同等、速度は1.0比2.5倍遅い | 平均88.6秒/タスク | thinking量が10〜17倍に増加 |
| study2形式（Aider自律バグ修正） | 機能的に成功 | 81秒 | パーサー誤爆（ゴミファイル3つ）が新規発生 |
| study3形式（Aider・カルマン/SVD） | **完全にFAIL** | 2.5時間（進展なし） | Aiderがthinking暴走を制御できない（`--thinking-tokens`が無効） |
| study4形式（monocoder・カルマン/SVD） | 1勝1敗 | 各9分程度 | monocoderなら安定して動く。新バグ（G6のpycacheキャッシュ問題）を発見・修正 |

**Ornith-1.5-9Bを実務で使うなら、Aiderのような汎用ハーネスより、thinkingパラメータを直接制御できるツール（monocoderのような自作ドライバ、あるいはthinking制御に対応したハーネス）を選ぶ方が安全です。** これはstudy4の結論（「ハーネスで防げる失敗と防げない失敗の境界」）を、新しいモデルでも再確認する形になりました。thinkingが長いモデルほど、ハーネス側の生成時間制御の有無がそのまま実用性を左右します。

## この結論が変わりうる条件

- study3（Aider経由）はSVDタスクを実際には試しておらず、Kalmanタスクの結果から類推してスキップした判断です
- Aiderの`--thinking-tokens`がこの特定のモデル識別子（`ollama/hf.co/ornith-ai/Ornith-1.5-9B-GGUF`）を認識しない問題は、Aider側の今後のアップデートやモデル識別子の指定方法を変えることで解消する可能性があります
- 各タスクとも1回の実行に基づく結果で、統計的なばらつきは未検証
