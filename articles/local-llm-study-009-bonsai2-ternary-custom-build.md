## この記事について

[Ternary Bonsai 2 27B](https://pc.watch.impress.co.jp/docs/news/2142052.html) は、[study7](https://zenn.dev/)・[study8](https://zenn.dev/) で検証した `Qwen3.8-27B` をベースに、三値（ternary）量子化で**元の1/9のサイズ（5.9GB）に圧縮しつつ精度98.2%を維持**したと謳うモデルです。

この記事の主眼は速度ではなく**精度劣化の度合い**です。study7で使った `Qwen3.8-27B`（`UD-Q2_K_XL`）は、9.83GBというファイルサイズから逆算すると約**2.9bit/weight**の事後量子化（PTQ）です。一方Bonsai 2は**1.75bit/weightと、より低いビット予算**で劣化を抑えることを狙っています。

この記事は2段構成です。

1. **ビルドの記録**（前半）: Ollamaでは動かせず、専用フォークのllama.cppをソースからビルドして動かした経緯
2. **同条件での測り直し**（後半）: 最初の版は、Bonsai 2を新しい環境で1回測り、Qwen3.8-27Bはstudy7の記録と比べるだけでした。そこで、**同じMac mini・同じllama-server・同じコンテキスト長・同じクライアント**で両方を測り直し、study1・study6・study2・study4の4形式を実行しました。その結果、最初の版の結論の一部は**再現しませんでした**。

あわせて、同じ三値量子化の小型版（2B / 4B / 9B）の結果も並べ、サイズによる変化を見ます（小型版の詳細は study10 にまとめています）。

## Ollamaでは動かせなかった

`ollama pull hf.co/prism-ml/Ternary-Bonsai-2-27B-gguf:PTQ1_0` でモデル自体はpullできましたが、`ollama show`・`ollama run` のどちらも次のエラーで失敗しました。

```
Error: tensor "output.weight" size overflow
```

モデルカードを確認すると、理由が明記されていました。

> Two GGUF packings with custom ternary hybrid-attention kernels for llama.cpp (CUDA, Metal)

**標準のllama.cpp（Ollamaが内部で使っているもの）では読めない、専用のテンソルレイアウトを使っている**とのことです。MLX版も同様に、PrismML独自のMLXフォークが必要と明記されていました。

## ソースからビルドする

モデル配布元は `PrismML-Eng/Bonsai-demo` という公式デモリポジトリを「実行時の一次情報源」として案内しています。中の `setup.sh` を読むと、**デフォルトではビルド済みバイナリをダウンロードし、macOSのGatekeeperを明示的に解除（`xattr -cr` + ad-hoc codesign）して実行する**仕組みになっていました。他人の未署名バイナリを実行許可付きで走らせる操作なので、これはひとまず避け、`build_mac.sh`（ソースから手元でビルドする方のスクリプト）を選びました。自分でコンパイルしたバイナリへの ad-hoc codesign は通常の挙動で、他人のバイナリのGatekeeper解除とは性質が異なります。

### ビルドで実際に踏んだエラー

`PrismML-Eng/llama.cpp`（prismブランチ）をクローンし、CMakeでMetal対応ビルドを実行したところ、次のエラーで失敗しました。

```
cc: error: unsupported argument 'native' to option '-mcpu='
```

原因を追ったところ、llama.cppのCPUバックエンド検出ロジックが `-mcpu=native` を使ってこのMacのApple Clang（21.0.0、Xcode CLT経由）にCPU機能を問い合わせていましたが、**このコンパイラは `-mcpu=native` という引数自体を受け付けない**ことが分かりました（プローブの結果が空になり、フォールバックとして文字通り `-mcpu=native` を渡してしまい、それがコンパイルエラーになるという二段階の失敗でした）。

`-DGGML_NATIVE=OFF` を追加してこの自動検出を無効化したところ、ビルドが正常に完了しました。

```sh
cmake -B build-mac \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_OSX_ARCHITECTURES=arm64 \
    -DCMAKE_OSX_DEPLOYMENT_TARGET=14.0 \
    -DGGML_METAL=ON \
    -DGGML_METAL_EMBED_LIBRARY=ON \
    -DBUILD_SHARED_LIBS=OFF \
    -DGGML_STATIC=ON \
    -DLLAMA_OPENSSL=OFF \
    -DGGML_NATIVE=OFF
cmake --build build-mac -j$(sysctl -n hw.logicalcpu)
```

なお `llama-cli --version` の表示には `built with AppleClang ... for Darwin x86_64` と出ましたが、`file`・`lipo -info` で確認したところ実体は正しく `arm64` でした。バージョン文字列側の表示バグのようで、実害はありませんでした。

### モデルファイルの再利用

Ollama経由で一度pull済みだったモデル（5.95GB）は、Ollamaのblobストアにそのままの GGUF ファイルとして保存されていたため、再ダウンロードせずにllama-serverへ渡せました。マニフェストJSONに記載されたレイヤーサイズ（5,946,648,928バイト）とファイル実サイズが一致し、先頭バイトも `GGUF` マジックナンバーで始まっていることを確認しています。

### 実行時に踏んだもう1つのエラー：GPUメモリ不足

ビルドしたバイナリでモデルを起動したところ、今度は推論実行時に次のエラーが出ました。

```
error: Insufficient Memory (kIOGPUCommandBufferCallbackErrorOutOfMemory)
```

モデルのデフォルトコンテキスト長（262,144トークン）をそのまま使おうとしたため、KVキャッシュだけで16GB統合メモリを圧迫したのが原因でした。`-c` でコンテキスト長を明示的に制限したところ、正常に動作しました。後半の測り直しでは `-c 32768` を使い、27Bの2モデルとも（Mac mini、16GB）メモリ不足は起きませんでした。

## 測り直しの条件

最初の版には弱点がありました。Qwen3.8-27Bの数字は別の日・別の環境（旧MacBook）で測ったstudy7の値で、推論エンジンも違っていました。そこで今回は、Mac mini（Apple M6、メモリ16GB）で、**Bonsai 2 27BとQwen3.8-27B（UD-Q2_K_XL）を同じllama-server（PrismMLフォーク）・同じ `-c 32768` ・同じクライアント**で測りました。bits/weightは、ファイルサイズ×8÷パラメータ数で、パラメータ数は推論サーバーが読み込んだ値です。

| モデル | 量子化 | パラメータ | ファイル(GB) | bits/weight |
|---|---|---:|---:|---:|
| Bonsai 2 27B | PTQ1_0（三値） | 26.9B | 5.95 | 1.77 |
| Qwen3.8-27B | Q2_K（UD-Q2_K_XL） | 27.3B | 9.83 | 2.88 |

実行した4形式は、固定の入力を使っています。

- **study1形式**: コードレビュー、FizzBuzz、バグ検出、デコレーター説明の4タスクを各1回
- **study6形式**: 約8,300文字の記事を「3〜5個の箇条書きで要約」させ、個数を機械的に数える（1回）
- **study2形式**: Aiderの `--auto-test` で境界値バグを自律修正。実行前後のテストファイルを比較して改竄を検知（1回）
- **study4形式**: 自作のmonocoderで、計画→実装＋テスト→ドキュメント化を、カルマンフィルタとSVDで各2回

出力はすべて私が読みました。自動チェック（簡体字スキャン、FizzBuzzの手書き列挙の検算、箇条書きの個数）は文字しか見ないので、それだけでは足りないためです。

## 結果：27Bどうしの比較

### 一覧

| 観点 | Bonsai 2 27B（1.77bit） | Qwen3.8-27B（2.88bit） |
|---|---|---|
| 簡体字の混入（4タスク＋要約） | 0件 | 0件 |
| FizzBuzzの手書き出力例 | 誤り4件（17〜20番目） | 誤り4件（5・10・15・20番目） |
| コードレビュー | 正確 | 正確 |
| バグ検出 | 正確 | 正確（無関係な箇条書きが1つ） |
| デコレーター説明 | Pythonの `@` 構文を正しく説明 | デザインパターンのDecoratorを説明（`@` に触れず） |
| 要約（3〜5個） | 4個 | 3個 |
| Aider（修正・テスト改竄） | 修正成功・改竄なし（37.8秒） | 修正成功・改竄なし（87.7秒） |
| monocoder カルマン | **0/2**（2回とも6試行で失敗） | **2/2**（2試行、1試行で成功） |
| monocoder SVD | 1/2（成功は4試行目、失敗は6試行） | 1/2（成功は1試行目、失敗は6試行） |
| study1の出力速度 | 約40文字/秒（5,318文字÷133.6秒） | 約14文字/秒（4,870文字÷340.0秒） |

### 最初の版の結論は、再現しませんでした

最初の版では、Qwen3.8-27Bに見られた「簡体字の混入（型チェックに関する文中の中国語の語など、2箇所）」「FizzBuzzの手書き列挙ミス」「不自然な言い回し」が、Bonsai 2では**4タスクとも出なかった**ことを根拠に、「低いビット予算でも劣化の兆候が少ない」と書きました。同条件で測り直すと、次のようになりました。

- **簡体字の混入**: Qwen3.8-27Bも0件でした。study7の2箇所は、今回は出ていません。同じモデル・同じプロンプトでも、生成のたびに出たり出なかったりする程度のものだったと見るのが妥当です。
- **FizzBuzz**: どちらも手書きの出力例に誤りがありました（コードは両方とも正確）。Bonsai 2は最後の4項目（17が `Fizz`、18が `18`、19が `Buzz`、20が `FizzBuzz`）、Qwen3.8-27Bは `Buzz` を一度も出さず15番目も `Fizz` でした。最初の版でBonsai 2の「完全に正確」とした出力は、1回目の偶然だった可能性があります。
- **デコレーター**: 逆転しました。今回はBonsai 2がPythonの `@` 構文（複数のデコレーターの重ね方、引数付きのデコレーターまで）を正しく説明し、Qwen3.8-27Bはクラスで包むデザインパターンの説明に終始しました。

つまり、最初の版は**1回ずつの出力の差を、量子化方式の差と読んでしまった**ことになります。4タスク・各1回の比較で「兆候が0件か2件か」という差は、同じ条件で再実行しただけで消えました。

### 差が出たのは、自律的な複数ステップの作業と速度

測り直しで安定して差が見えたのは、次の2点です。

**monocoder（計画→実装＋テスト→ドキュメント化）**: カルマンフィルタで、Bonsai 2は2回とも失敗し、Qwen3.8-27Bは2回とも成功しました。Bonsai 2の失敗は6回の試行（2セッション×3反復）を使い切ったもので、サーバーエラー（コンテキスト長不足など）ではなく、モデルの出力の問題です。SVDは両モデルとも1/2で、差は見えません。合計では Bonsai 2が1/4、Qwen3.8-27Bが3/4です。**小さな差ですが、同じ方向で出たのはカルマンだけなので、断定はしません。**

**速度**: 同じエンジン・同じ環境で、Bonsai 2はstudy1の出力が約2.8倍速く（文字数あたり）、Aiderの修正は約2.3倍（37.8秒対87.7秒）、要約は約2.5倍（34.8秒対86.4秒）でした。monocoderの1回あたりの時間は、Bonsai 2が失敗を含めて397〜594秒、Qwen3.8-27Bは成功した3回が976〜1,078秒でした（失敗した1回は2,137秒）。

最初の版には「速度はほぼ同等で、圧縮の恩恵は見られない」と書き、三値のビット展開のオーバーヘッドが相殺していると推測しました。しかし、この推測は**取り下げます**。あの比較は、Bonsai 2を旧MacBookで測った値と、Qwen3.8-27Bをstudy7（別の日・別のエンジン）で測った値の並べ方で、条件が揃っていませんでした。同条件で測ると、三値の方が明確に速くなりました。

### 参考：旧MacBookでの1回測定

記事にしていなかった旧MacBook（Apple M4、メモリ16GB）での測定が、Bonsai 2 27Bで3つあります。いずれも1回で、Mac miniの結果とは直接比べられません。

- Aider（study2形式）: 修正成功、103秒（Qwen3.8-27Bはstudy7の記録で193秒）
- 3段階のカルマンフィルタ（study3形式）: 段階1は399秒で成功。段階2はAiderのクライアント側タイムアウトで失敗しました。これはモデルの能力ではなく、長い出力に対するクライアント側の待ち時間の上限が原因です
- ドキュメント生成（docgen）: 1段の組み立てが479.5秒で成功

長い出力でAiderが失敗するのは、モデルの優劣ではなくクライアント側の上限の問題でした。

## サイズによる変化：Bonsai 2の2B / 4B / 9B / 27B

同じ三値量子化の小型版も、同じ条件で測りました。9Bには同じ系統の通常量子化（Qwen3.5、Q4_K_M、約5bit）を、4Bと2Bにも同サイズの通常量子化を対照として測っています（詳細は study10）。27Bの対照は、Qwen3.8-27B（約2.9bit）です。

| サイズ | 三値 FizzBuzz | 三値 要約 | 三値 Aider | 三値 monocoder | 通常量子化の対照 |
|---|---|---|---|---|---|
| 2B | `Fizz`/`Buzz` を出さない | 10個（範囲外） | 失敗（出力形式に従えず） | 0/4 | 要約・Aiderは通常が良好、monocoderは0/4 |
| 4B | 誤り5件 | 4個（抜けあり） | 成功 | 0/4 | FizzBuzz誤り1件、monocoderは0/4 |
| 9B | 正確 | 4個 | 成功 | 1/4 | 全体としてほぼ同等、monocoderは1/4 |
| 27B | 誤り4件 | 4個 | 成功 | 1/4 | Qwen3.8-27B: 誤り4件、3個、成功、3/4 |

小さい方（2B・4B）では、同サイズの通常量子化より基礎的な質問や指示への追従で崩れた箇所が多く、9Bと27Bでは、主要な結果の差は小さくなります。ただし27Bだけは、monocoderで通常量子化（Qwen3.8-27B）の方が良好でした。出力速度は、同じエンジンで、三値が通常量子化の約1.9〜2.8倍でした（9Bが約2.2倍、4Bが約1.9倍、2Bが約2.3倍、27Bが約2.8倍）。

## 考察

測定した範囲で言えることだけを書きます。いずれも1回（monocoderのみ2回）の結果です。

**最初の版の「低ビットでも劣化の兆候が少ない」は、同条件の再測定では裏付けられませんでした。** 27Bの単発の質問（レビュー、バグ検出、要約）では、三値と通常量子化で目立つ差はありませんでした。FizzBuzzの出力例はどちらも誤り、デコレーターは三値の方が良く、簡体字の混入はどちらも0件でした。「1.77bit/weightで、2.88bit/weightの通常量子化と同程度の単発の回答」は、この4タスクでは成り立っています。それがモデルカードの「98.2%の精度」を支持するかどうかは、こうした簡易チェックでは言えません。

**差が見えたのは、自律的な複数ステップの作業（monocoderのカルマン）でした。** 三値は2回とも失敗、通常量子化は2回とも成功です。ただし各2回で、SVDでは差が出ていません。「複数ステップで崩れやすい」という方向の示唆に留まります。

**速度は、三値の明確な利点でした。** 同じ条件で約2.3〜2.8倍速く、ファイルサイズも約6割です。16GBのMac miniで、このサイズの27Bを実用的な速度で動かせる点は、通常量子化との差として確かにあります。

**サイズを下げると、三値の方が先に崩れる傾向があります。** 2B・4Bで基礎的な質問に崩れた箇所が多く、9B以上ではその差が小さくなりました。ただし、これは1回ずつの出力の比較であり、偶然の可能性が残ります。

## まとめ

| 観点 | 結果 |
|---|---|
| Ollamaでの動作 | 不可（専用テンソルレイアウトのため） |
| ソースビルド | 成功（`-DGGML_NATIVE=OFF` が必要だった） |
| 27Bの単発4タスク・要約 | 三値と通常量子化で、目立つ差なし（同条件） |
| 27Bのmonocoder | 三値 1/4、通常 3/4（カルマンで差、SVDは同じ） |
| 27Bの速度（同条件） | 三値が約2.3〜2.8倍速い |
| サイズによる変化 | 2B・4Bで三値の方が崩れやすく、9B以上は差が小さい |
| 導入の手間 | 大きい（ソースクローン・CMakeビルド・GPUメモリ調整が必要） |

**三値量子化の謳い文句（低ビットでも劣化を抑える）は、27Bの単発の回答では保たれていましたが、自律的な複数ステップの作業では通常量子化に及ばない兆候がありました。** 最初の版で書いた「兆候が0件か2件か」という差は、測り直しで消えています。同じ条件で、複数回測るまで、単発の差は結論にしない、というのが今回の教訓です。

## この結論が変わりうる条件

- 精度の比較は「4タスク・各1回の出力を読んだ定性評価」で、パープレキシティやベンチマークスコアのような定量評価ではありません。サンプル数を増やせば、FizzBuzzやデコレーターの差は入れ替わるかもしれません
- monocoderは各2回です。n=2は統計ではなく、結果が割れるかを見るための回数です
- 27Bの比較は、同じ `-c 32768`・同じエンジンで揃えましたが、Bonsai 2のGGUFはPrismMLフォーク専用で、通常量子化のGGUFも同じフォークで動かしています。標準のllama.cppでは、通常量子化の速度が変わる可能性があります
- ビルドは `-DGGML_NATIVE=OFF` で行ったため、SIMD最適化が効いていない可能性があります。`GGML_CPU_ARM_ARCH` を明示指定すれば速度が変わるかもしれません
- より軽い量子化（PQ2_0、7.21GB）は測っていません
- 旧MacBookでの測定（Aider、3段階、docgen）は1回ずつで、Mac miniの結果と直接比べられません
