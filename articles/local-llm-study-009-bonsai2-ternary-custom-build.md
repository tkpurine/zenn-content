## この記事について

[Ternary Bonsai 2 27B](https://pc.watch.impress.co.jp/docs/news/2142052.html) という、[study7](https://zenn.dev/)・[study8](https://zenn.dev/) で検証した `Qwen3.8-27B` をベースに、三値（ternary）量子化で**元の1/9のサイズ（5.9GB）に圧縮しつつ精度98.2%を維持**したと謳うモデルが公開されました。

この記事の主眼は速度ではなく**精度劣化の度合い**です。study7で使った `Qwen3.8-27B`（`UD-Q2_K_XL`）は、9.83GBというファイルサイズから逆算すると平均**約2.9bit/weight**の量子化で、いわゆる「2bit級」の事後量子化（PTQ）にあたります。study7では実際に、簡体字の混入やFizzBuzzの手書き列挙ミスといった**具体的な精度劣化の兆候**が見つかりました。

一方Bonsai 2は、**1.75bit/weightとQwen3.8-27Bより低いビット予算にもかかわらず**、三値量子化という別アプローチで精度劣化を抑えることを狙ったモデルです。同じstudy1形式の4タスクを実行し、**より低いビット予算で、より劣化の兆候が少ないか**を比較するのが今回の本題です。

もう1つ、このシリーズでは毎回 `ollama pull` 一発（または `hf.co/...` 経由の直接pull）で気軽に検証してきましたが、今回は**その前提が初めて崩れました**。Ollamaでは動かせないモデルで、動かすには専用フォークのllama.cppをソースからビルドする必要がありました。この記事はその記録も兼ねています。

## Ollamaでは動かせなかった

`ollama pull hf.co/prism-ml/Ternary-Bonsai-2-27B-gguf:PTQ1_0` でモデル自体はpullできましたが、`ollama show`・`ollama run` のどちらも次のエラーで失敗しました。

```
Error: tensor "output.weight" size overflow
```

モデルカードを確認すると、理由が明記されていました。

> Two GGUF packings with custom ternary hybrid-attention kernels for llama.cpp (CUDA, Metal)

**標準のllama.cpp（Ollamaが内部で使っているもの）では読めない、専用のテンソルレイアウトを使っている**とのことです。MLX版も同様に、PrismML独自のMLXフォークが必要と明記されていました。

## ソースからビルドする

モデル配布元は `PrismML-Eng/Bonsai-demo` という公式デモリポジトリを「実行時の一次情報源」として案内しています。中の `setup.sh` を読むと、**デフォルトではビルド済みバイナリをダウンロードし、macOSのGatekeeperを明示的に解除（`xattr -cr` + ad-hoc codesign）して実行する**仕組みになっていました。他人の未署名バイナリを実行許可付きで走らせる操作なので、これはひとまず避け、`build_mac.sh`（ソースから手元でビルドする方のスクリプト）を選びました。自分でコンパイルしたバイナリへの ad-hoc codesign は通常の挙動で、他人のバイナリのGatekeeper解除とは性質が異なります。

### ビルドで実際に踏んだエラー

`PrismML-Eng/llama.cpp`（prismブランチ）をクローンし、CMakeでMetal対応ビルドを実行したところ、次のエラーで失敗しました。

```
cc: error: unsupported argument 'native' to option '-mcpu='
```

原因を追ったところ、llama.cppのCPUバックエンド検出ロジックが `-mcpu=native` を使ってこのMacのApple Clang（21.0.0、Xcode CLT経由）にCPU機能を問い合わせていましたが、**このコンパイラは `-mcpu=native` という引数自体を受け付けない**ことが分かりました（プローブの結果が空になり、フォールバックとして文字通り `-mcpu=native` を渡してしまい、それがコンパイルエラーになるという二段階の失敗でした）。

`-DGGML_NATIVE=OFF` を追加してこの自動検出を無効化したところ、ビルドが正常に完了しました。

```sh
cmake -B build-mac \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_OSX_ARCHITECTURES=arm64 \
    -DCMAKE_OSX_DEPLOYMENT_TARGET=14.0 \
    -DGGML_METAL=ON \
    -DGGML_METAL_EMBED_LIBRARY=ON \
    -DBUILD_SHARED_LIBS=OFF \
    -DGGML_STATIC=ON \
    -DLLAMA_OPENSSL=OFF \
    -DGGML_NATIVE=OFF
cmake --build build-mac -j$(sysctl -n hw.logicalcpu)
```

なお `llama-cli --version` の表示には `built with AppleClang ... for Darwin x86_64` と出ましたが、`file`・`lipo -info` で確認したところ実体は正しく `arm64` でした。バージョン文字列側の表示バグのようで、実害はありませんでした。

### モデルファイルの再利用

Ollama経由で一度pull済みだったモデル（5.95GB）は、Ollamaのblobストア（`~/.ollama/models/blobs/sha256-...`）にGGUFファイルそのものとして保存されていたため、再ダウンロードせずシンボリックリンクで再利用できました。マニフェストJSONに記載されたレイヤーサイズ（5,946,648,928バイト）とファイル実サイズが一致し、先頭バイトも `GGUF` マジックナンバーで始まっていることを確認しています。

### 実行時に踏んだもう1つのエラー：GPUメモリ不足

ビルドしたバイナリでモデルを起動したところ、今度は推論実行時に次のエラーが出ました。

```
error: Insufficient Memory (kIOGPUCommandBufferCallbackErrorOutOfMemory)
```

モデルのデフォルトコンテキスト長（262,144トークン）をそのまま使おうとしたため、KVキャッシュだけで16GB統合メモリを圧迫したのが原因でした。`-c 8192` でコンテキスト長を明示的に制限したところ、正常に動作しました。

## study1形式の4タスクで検証：着目は精度劣化の兆候

ビルドしたバイナリで、study1・study7と同じ4タスクを実行しました。

**結果：4タスクとも、study7のQwen3.8-27Bで見つかった精度劣化の兆候が一切再現しませんでした。**

| 精度劣化の兆候 | Bonsai 2 27B（PTQ1_0、1.75bit/weight） | Qwen3.8-27B（UD-Q2_K_XL、約2.9bit/weight、study7） |
|---|---|---|
| FizzBuzzの手書き列挙ミス | **なし**（コード・出力例とも完全に正確） | **あり**（コードは正しいが、手書きの出力例の末尾3項目が誤り） |
| 簡体字（中国語）の混入 | **なし**（4タスクとも確認せず） | **あり**（「型チェックが**缺失**している」等、2箇所） |
| 不自然な言い回し | **なし** | **あり**（「**被**デコレーター」など中国語の受身構文に近い表現） |
| デコレーターの解釈 | 正確（Python固有の`@decorator`構文に正しく言及） | 正確 |
| コードレビュー・バグ検出の論理 | 正確 | 正確 |

**注目すべきは、Bonsai 2の方がQwen3.8-27Bより低いビット予算（1.75bit/weight vs 約2.9bit/weight）でありながら、劣化の兆候が少なかった点です。** モデルカードが謳う「三値量子化により、より低ビットでも精度劣化を抑える」という設計思想と、方向性としては一致する結果でした。

もちろんこれは、コード生成・簡単な説明という4タスク・各1回の実行から見えた**定性的な兆候の比較**であり、パープレキシティやベンチマークスコアのような定量評価ではありません。「本当に98.2%の精度を維持しているか」を厳密に検証したわけではない点には注意が必要です。とはいえ、**同じ簡易チェックで一方には複数の具体的な不具合が見つかり、もう一方には見つからなかった**という事実は、量子化アプローチの違いを考える上で十分に参考になる材料だと思います。

### 所要時間（参考）

| タスク | Bonsai 2 27B | Qwen3.8-27B（study7） |
|---|---:|---:|
| コードレビュー | 153秒 | 133秒 |
| FizzBuzz | 46秒 | 44秒 |
| バグ検出 | 145秒 | 126秒 |
| デコレーター説明 | 138秒 | 185秒 |
| **平均** | **120.5秒** | **122秒** |

ファイルサイズは9.83GB→5.95GBと約1.65分の1に縮小しましたが、速度はほぼ変わりませんでした。「9分の1圧縮」はディスク容量・メモリ占有量の話であり、体感速度の向上には直結しないようです（三値量子化特有のビット展開計算のオーバーヘッドが、サイズ削減分の速度メリットを相殺していると考えられます）。ただしこの記事の主眼はあくまで精度劣化の比較であり、速度は副次的な観測に留めています。

## まとめ

| 観点 | 結果 |
|---|---|
| Ollamaでの動作 | 不可（専用テンソルレイアウトのため） |
| ソースビルド | 成功（`-DGGML_NATIVE=OFF` が必要だった） |
| **精度劣化の兆候（4タスク中）** | **Bonsai 2: 0件 / Qwen3.8-27B（study7）: 2種類** |
| ビット予算 | Bonsai 2の方が低い（1.75bit/weight vs 約2.9bit/weight） |
| 速度 | ほぼ同等（圧縮による恩恵は見られず） |
| 導入の手間 | 大きい（ソースクローン・CMakeビルド・GPUメモリ調整が必要） |

**低いビット予算でも劣化を抑える、という三値量子化の謳い文句は、今回の簡易チェックの範囲では裏付けられる結果でした。** 同じ4タスクをQwen3.8-27B（約2.9bit/weight、通常のPTQ）に投げたときに見つかった簡体字混入や手書き列挙ミスが、より低ビットのBonsai 2（1.75bit/weight）では一切見られなかったことは、量子化アプローチそのものの差が実際のアウトプット品質に表れている可能性を示しています。

一方で、このシリーズの前提だった「Ollamaで気軽にpullして試す」が通用しないモデルだった点、得られた速度メリットが期待したほどではなかった点は、導入コストとして正直に記録しておきます。

## この結論が変わりうる条件

- 精度劣化の比較は「4タスク・各1回の実行で見つかった兆候の有無」という粗い定性評価であり、パープレキシティなどの定量的なベンチマークではありません。サンプル数を増やす、あるいは実際のベンチマークスイートで検証しないと、今回の傾向が偶然でないとは言い切れません
- より軽い量子化（PQ2_0、7.21GB）や、GPUメモリ不足を避けるための`-c`設定の最適化を行えば、速度が変わる可能性があります
- 自律タスク（study2〜4形式）やAider経由での検証は行っておらず、Bonsai 2固有のクセ（thinking暴走の有無など）は未確認です
- 今回はCPUバックエンドの自動検出を無効化（`-DGGML_NATIVE=OFF`）してビルドしたため、SIMD最適化が効いていない可能性があります。原因を特定した上で`GGML_CPU_ARM_ARCH`を明示指定すれば、速度が改善するかもしれません
