## この記事について

[study12](https://zenn.dev/tkpurine/articles/local-llm-study-012-qwen-code) では、Qwen Code をローカルLLM5つで動かし、カルマンフィルタとSVDの実装を測りました。27B級の2モデル（Qwen3.8-27B、Ternary Bonsai 2 27B）は、1回の呼び出しを壁時間30分で打ち切ると、ほとんどの実行が結果の出ないまま終わり、「測定不能」として別に数えました。

この記事は、その追加検証です。壁時間を90分に伸ばして、同じ27B級の2モデルを測り直しました。結論を先に書くと、**壁時間を伸ばすだけでは足りませんでした**。最初の試行では、Qwen Code に壁時間とは別の「1回の応答の上限（既定15分）」があり、条件Aの4回がそこで止まっていました。この上限も延ばして測り直すと、Qwen3.8-27B は条件Aが4回中3回成功し、成功した5回の所要時間はすべて47〜76分でした。

## 検証したモデル

| モデル | 量子化 | bits/weight |
|---|---|---:|
| Qwen3.8-27B | UD-Q2_K_XL | 2.88 |
| Ternary Bonsai 2 27B | PTQ1_0 | 1.77 |

## 検証方法

study12 と同じタスク（カルマンフィルタ、SVD）と判定を使いました。違いは壁時間と、Qwen Code の上限設定です。

- **タスクと条件**: カルマン・SVD、条件A（直接実装）と条件B（plan modeで計画してから実装）、各 n=2。推論（thinking）はオンのまま
- **壁時間**: 1回の呼び出しを5400秒（90分）まで。study12 は30分
- **サーバー**: llama-server、`-c 32768`、1モデルずつ。メモリ16GBのMac mini（Apple M6）
- **最初の試行**（Qwen3.8-27Bのみ）: 壁時間だけを90分にした
- **設定修正後の測り直し**: Qwen Code の `QWEN_STREAM_MAX_LIFETIME_MS`（1回のストリーミング応答の総待ち時間。既定900000ms＝15分）と `QWEN_CODE_API_TIMEOUT_MS` を5400000msにし、無通信による切断を無効にし、`contextWindowSize` をサーバーの値より4096小さくして、Qwen Code が早めに会話を圧縮するようにした
- **比較対象**: study12 の30分（推論オン）と、別セッションで測った推論オフ（30分）

## 結果

### 最初の試行（壁時間だけを90分にした、Qwen3.8-27B）

| 条件 | カルマン | SVD |
|---|---|---|
| A（直接実装） | 0/2 | 0/2 |
| B（計画→実装） | 1/2 | 1/2 |

条件Aの4回は、4回とも約45分（2715秒前後）に `error_during_execution` で終了し、ツール呼び出しは1回も完了していませんでした。壁時間の90分には届いていません。

### 設定修正後の測り直し

| モデル | カルマン A | カルマン B | SVD A | SVD B |
|---|---|---|---|---|
| Qwen3.8-27B | 2/2（平均3398s） | 1/2（平均4790s） | 1/2（平均4457s） | 1/2（平均5255s） |
| Ternary Bonsai 2 27B | 0/2（平均2947s） | 0/2（平均6198s） | 2/2（平均919s） | 2/2（平均3442s） |

### 同じモデルを、壁時間と推論で並べる（Qwen3.8-27B）

カルマンとSVDの A/B 各条件で、成功数／実行数を並べます（壁時間切れの数を括弧に添えます）。推論オフは n=5、ほかは n=2 です。

| 設定（Qwen3.8-27B） | カルマン A | カルマン B | SVD A | SVD B |
|---|---|---|---|---|
| 推論オン・30分（study12） | 測定不能（壁時間切れ2/2） | 測定不能（壁時間切れ2/2） | 測定不能（壁時間切れ2/2） | 測定不能（壁時間切れ2/2） |
| 推論オン・90分（設定修正後） | 2/2 | 1/2 | 1/2 | 1/2 |
| 推論オフ・30分（n=5） | 4/4（壁時間切れ1） | 4/4（壁時間切れ1） | 4/5 | 4/4（壁時間切れ1） |

推論オフの成功した16回の所要時間は、482〜2112秒（8〜35分）でした。推論オン・90分で成功した5回は47〜76分です。バグ修正（study2）は推論オフで A/B とも5/5でした（平均135秒と284秒）。

推論オフは壁時間が30分のままでも、推論オン・90分と同じ程度に成功しています。ただし、推論オフの失敗4回のうち壁時間切れが3回あり、30分では足りない実行も残っています。

### Bonsai 2 27B も推論オフで測り直した

| 設定（Bonsai 2 27B） | バグ修正 A | バグ修正 B | カルマン A | カルマン B | SVD A | SVD B |
|---|---|---|---|---|---|---|
| 推論オン・90分（n=2） | — | — | 0/2 | 0/2 | 2/2 | 2/2 |
| 推論オフ・30分（n=5） | 5/5 | 5/5 | 5/5 | 1/4（壁時間切れ1） | 4/5 | 2/5 |

Bonsai 2 27B は、推論オフにするとカルマン A が0/2から5/5になりました。一方、条件B（plan modeで計画してから実装）では、カルマンが1/5、SVDが2/5と大きく下がります。失敗の多くは40ターンの上限で、収束しなかった実行です（カルマン B は5回中4回、SVD B は5回中2回で、計画か実装がこの上限に当たりました）。条件Aは14/15、条件Bは8/15でした。

推論ブロックを数えると、推論オフの実行ログは Qwen3.8-27B が45本、Bonsai 2 27B が41本で、どちらも0件でした。サーバーが推論オフだったことは確認できています。

## 条件Aが45分で止まっていた原因

最初の試行の条件Aは、どの実行も約45分（2711〜2719秒）で止まっていました。ほぼ同じ秒数だったので、固定の時間制限を疑い、Qwen Code の設定を調べると、次の上限がありました。

- `QWEN_STREAM_MAX_LIFETIME_MS`: 1回のストリーミング応答の総待ち時間。既定900000ms（15分）。`settings.json` では変更できず、環境変数のみ
- `QWEN_CODE_API_TIMEOUT_MS`: 既定120秒
- `streamIdleTimeoutMs`: 無通信で切断。既定240秒

ログでは、止まった4回とも、再試行を示す "Retrying provider attempt" が2回出ていました。15分×3回で約45分になり、秒数とも合います。また、止まった4回のログには、推論のブロックが3つずつ（合計約4.4〜4.7万字）残っていました。1回の試行で約1.5万字、15分で出し切れず、**最初のツール呼び出しに進む前に、推論の途中で打ち切られていた**と考えられます。

この上限は壁時間とは別なので、study12 の30分の測定にも効いていた可能性があります。

## 考察

表の実測値から言えることだけを書きます。

**壁時間と1応答の上限を両方伸ばすと、Qwen3.8-27B の条件Aは解けました。** 4回中3回が成功し、最初の試行の0/4から変わっています。成功した5回（A が3回、B が2回）の所要時間は47〜76分で、study12 の壁時間30分では、成功しようがありませんでした。

**Ternary Bonsai 2 27B は、SVD は成功し、カルマンは失敗しました。** SVD は条件A・Bの4回すべて成功し、Aは10分と20分で終わっています。カルマンは4回すべて失敗し、うち2回（A run2 と B run2 の実装の呼び出し）は、ツールを1回も呼ばずに応答だけして終了していました。壁時間を伸ばしても、カルマンの結果は変わりませんでした。

**終了コード1で終わった実行が6件あり、原因はログのエラーメッセージで分かれました。** 4件（Qwen3.8 が3件、Bonsai が1件）は、リクエストが32768トークンのコンテキストを32878〜33710トークンで超えたことによる HTTP 400 です。`contextWindowSize` を4096小さくして会話の圧縮を早めても、圧縮が間に合わなかったことになります。残る2件（Qwen3.8 の SVD A と Bonsai のカルマン B）は「ツール結果の直後にモデルのストリームが進捗なく終了した」というエラーで、サーバー側の原因は、ログが残っていないため確認できませんでした。推論オフの Bonsai の終了コード1の2件も、同じコンテキスト超過でした。

**壁時間を伸ばすよりも、推論を切るほうが、同じ成功数に早く届きました。** Qwen3.8-27B のカルマン・SVD（A/B、計20回）は、推論オフの30分で16回成功しています（壁時間切れ3回を含めた20回に対する数です）。推論オン・90分は8回中5回の成功で、成功した実行は47〜76分かかりました。推論オフの成功は8〜35分で終わっています。ただし、推論オフは n=5、推論オンは n=2 で、サーバーの起動条件も別セッションで揃えたものなので、成功率の差は断定できません。

**Bonsai 2 27B は、推論オフで条件Aが大きく改善し、条件Bが悪化しました。** カルマン A は0/2から5/5へ、SVD A は2/2から4/5でした。条件Bは、40ターンの上限で止まる実行が目立ちます。plan mode の計画を渡されると、実装が長引いて収束しないように見えます。ただし、ログを詳しく読んだわけではなく、原因までは確定できません。

**plan mode の効果は、モデルによって逆向きでした。** Qwen3.8-27B は推論オフで A 13/15、B 13/15 と同じでした。Bonsai 2 27B は A 14/15、B 8/15 でした。

## まとめ

| 問い | 答え |
|---|---|
| 壁時間を90分にすると、27B級の「測定不能」は解けたか | Qwen3.8-27B は5/8が成功。ただし1応答の上限（既定15分）も延ばす必要があった |
| 推論を切るとどうなるか | Qwen3.8-27B は30分のまま16/20が成功（所要8〜35分）。Bonsai 2 27B の条件Aも大きく改善 |
| plan mode は効くか | Qwen3.8-27B は同じ、Bonsai 2 27B は推論オフで下がった（A 14/15、B 8/15） |

27B級を Qwen Code で測るときは、壁時間だけでなく、1応答の上限と推論の有無を揃えて測る必要があります。

## この結論が変わりうる条件

- 各条件 n=2 で、成功率は測れていません
- 設定修正後の測り直しは、壁時間以外にも条件が変わっています（1応答の上限、無通信の切断、contextWindowSize）。「壁時間を伸ばした効果」だけを切り出すことはできません
- 最初の試行の結果は、設定が不十分だった測定として残しています。Bonsai は最初の試行を測っていません（ドライバーの競合で開始できなかった）
- 終了コード1の6件のうち4件はコンテキスト超過で、モデルの実装力ではなくハーネスの設定による失敗です。残る2件はサーバー側の原因を確認できていません。成功判定は出力ファイルで行っており、終了コード1でも成功と判定された実行があります（Qwen3.8 のカルマン A run1）
- メモリ16GBでは、27B級の実行中の空きがほぼゼロでした。所要時間はメモリ圧迫の影響を含みます
- 実行環境は Apple M6、16GB です。他のチップでは所要時間が変わります
