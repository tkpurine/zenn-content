## この記事について

[PC Watchの記事](https://pc.watch.impress.co.jp/docs/news/2134411.html)で、`Qwen3.8-27B` にUnslothの Dynamic v3.0 量子化を適用したモデルが紹介されていました。1bit量子化（UD-IQ1_S、6.2GB）でも「トップ層の精度を約72%維持」という主張や、逆に「エージェントタスクでは精度が25%→8〜10%まで落ちる」という注記もあり、実際にどの程度なのか気になったので手元で試しました。

27Bという規模はこのシリーズで扱ってきた9Bクラスのモデルより大きく、16GB統合メモリのMacBookでは素の`Q4_K_M`（16.46GB）は実質的に厳しいため、記事でも紹介されている**`UD-Q2_K_XL`（9.83GB）**を使って検証しました。

## 検証方法

study1と同じ4タスクを、`think: false`を指定してOllama APIに直接投げました。

1. コードレビュー（`divide(a, b)` 関数）
2. FizzBuzz生成（1〜20）
3. バグ検出（`calculate_average` 関数、文脈依存バグ）
4. デコレーターの日本語説明

| 項目 | 内容 |
|---|---|
| モデル | `hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q2_K_XL`（Q2_K相当、9.83GB） |
| アーキテクチャ | qwen35、27.3Bパラメータ、コンテキスト長262144 |
| チップ / メモリ | Apple M4 / 16GB統合メモリ |

## 結果：速度

| タスク | 所要時間 |
|---|---:|
| コードレビュー | 133秒 |
| FizzBuzz | 44秒 |
| バグ検出 | 126秒 |
| デコレーター説明 | 185秒 |

このシリーズで検証してきた9Bクラスのモデル（Ornith-1.0-9Bは12〜60秒程度）と比べると、明確に遅い結果でした。27Bという規模の大きさが、量子化による圧縮効果を上回っている形です。

## 結果：内容の質 ── Q2_K量子化の代償が2箇所で見えた

論理面はしっかりしており、コードレビューでは型チェック・ゼロ除算・docstringまで踏み込んだ改善案を、バグ検出タスクでも文脈依存の判定を正確に行いました。ただし、2点気になる問題がありました。

### 1. FizzBuzzタスクで、手書きした出力結果が実際に間違っていた

モデルは正しいPythonコードを提示した一方、その**説明文中に手書きした「出力結果」の末尾が誤っていました**。

```
モデルの手書き出力（誤り）: ... 16, 17, 18, Buzz, Fizz
正しい出力:                 ... 16, 17, Fizz, 19, Buzz
```

提示したコード自体（`i % 15 == 0` → FizzBuzz、`i % 3 == 0` → Fizz、`i % 5 == 0` → Buzz）は完全に正しく、実行すれば正しい結果が出ます。**コード生成は正確なのに、それを手で書き下した列挙だけが間違っている**という珍しいパターンで、Q2_Kという強い量子化が「注意深い手計算・カウント」のような処理に影響している可能性があります。

### 2. 簡体字（中国語）の混入

コードレビュータスクで、次のような表現が2箇所ありました。

> 型チェックが**缺失**している
> ドキュメントが**缺失**している

「缺失」は中国語の簡体字で、正しい日本語は「欠如」または「欠けている」です。デコレーター説明タスクでも「**被**デコレーター」という、中国語の受身構文に近いやや不自然な言い回しが見られました。Qwenファミリーはもともと中国語圏のモデルであり、量子化によって言語選択の確度が揺らいだ結果、学習データに大量に含まれる中国語表現が漏れ出した可能性があります。

## 追試：資料作成・要約用途での検証

[study6](https://zenn.dev/) で `gemma4:e4b` と `qwen3.5:9b` に対して行った要約タスク（自作の技術記事、約8,400文字を「3〜5個の箇条書きで要約して」と指示）を、同じ条件でQwen3.8-27Bにも実行しました。

なお、この要約プロンプトはOllamaのデフォルトコンテキスト長（4096トークン）を超えたため、当初`context size exceeds`エラーで失敗しました。`num_ctx: 16384`を明示して再実行しています（27Bクラスのモデルを長文タスクに使う場合は、このデフォルト値の小ささに注意が必要です）。

| モデル | 所要時間 | 指示（3〜5個の箇条書き）への追従 | 簡体字の混入 |
|---|---:|---|---|
| gemma4:e4b（study6） | 93秒 | ✗ 無視して長大なレポート形式で応答 | なし |
| qwen3.5:9b（study6、think:false） | 112秒 | ✗ 無視して長大なレポート形式で応答 | なし |
| **Qwen3.8-27B（本記事）** | **398秒** | **✓ 正確に5個の箇条書きで応答** | **なし** |

**Qwen3.8-27Bは、study6で検証した2モデルがどちらも無視した「簡潔な箇条書きで」という指示に、唯一正確に従いました。** 内容も元記事の要点（`--edit-format whole`の採用理由、`qwen2.5-coder:7b`のテスト改竄、`gemma4:e2b`の意外な強さ、diffチェックによる安全策、次回への引き継ぎ方針）を過不足なく拾えており、単発タスク（前半の4タスク）で見られた簡体字の混入もこの要約タスクでは発生しませんでした。

一方で所要時間は398秒（約6.6分）と、gemma4:e4bの4倍以上かかっています。**「指示への追従性」と「速度」のどちらを優先するかで、資料作成用途の最適解は変わります。** 手早く済ませたい日常的な要約にはgemma4:e4b、フォーマットを厳密に守らせたい・時間はかけてよい用途にはQwen3.8-27B、という使い分けが妥当そうです。

## まとめ

| 観点 | 単発タスク（4タスク） | 要約タスク |
|---|---|---|
| 速度 | 9Bクラスより明確に遅い | gemma4:e4bの4倍以上（398秒） |
| 論理的な正確さ | 高い（コードレビュー・バグ検出とも的確） | 高い（元記事の要点を過不足なく抽出） |
| 手書き列挙の正確さ | 1件、計算ミスを確認（FizzBuzzの出力例） | ─ |
| 言語の純度 | 簡体字の混入を複数回確認 | 混入なし |
| 指示追従性 | ─ | ✓（gemma4:e4b・qwen3.5:9bは同条件で失敗） |

「1bit量子化でも精度72%維持」という記事の主張を直接検証したわけではありません（今回はバランス型のUD-Q2_K_XLのみ）が、**量子化を強めた27Bモデルでも、コード生成という「型のある」タスクは崩れにくい一方、手書きの数値列挙や言語選択という「細かい注意力」が必要な部分から先に精度が落ちる**、という傾向が見えました。同時に、**「指示への厳密な追従」という点では、このシリーズで検証した資料作成向け候補（gemma4:e4b・qwen3.5:9b）よりQwen3.8-27Bの方が優れている**という、当初想定していなかった長所も見つかりました。

## この結論が変わりうる条件

- 検証は各タスク1回の実行のみで、統計的なばらつきは未検証
- より強い量子化（UD-IQ1_S、6.2GB）や、より緩い量子化（UD-Q4_K_M以上）との比較は行っていません。記事が主張する「1bit量子化でも72%維持」を検証するには、複数の量子化度を横並びで比較する必要があります
- エージェントタスク（自律的な複数ステップの作業）での精度低下（記事によれば25%→8〜10%）は、本記事の単発Q&Aタスクでは検証できていません
